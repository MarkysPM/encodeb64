자주 발생하는 Base64 오류와 해결 방법

2026년 11월읽는 시간 약 8분

Base64는 단순하지만 프로그래밍에서 가장 혼란스러운 오류 메시지를 만들어 내곤 합니다. Incorrect padding, Invalid character, The input is not a valid Base-64 string 같은 것들입니다. 메시지는 언어마다 다르지만 원인은 거의 항상 같은 몇 가지입니다. 이 가이드는 확인해야 할 순서대로 원인을 나열하고 각각의 증상, 원인, 해결책을 설명합니다.

첫 단계: 문자열을 살펴보기

코드를 바꾸기 전에, 디코딩하려는 실제 문자열을 먼저 보세요. 네 가지 빠른 확인으로 대부분의 의문이 풀립니다.

  • -나 _가 들어 있나요? 그렇다면 표준 Base64가 아니라 Base64URL입니다.
  • +나 /가 들어 있나요? 그렇다면 표준 Base64입니다.
  • =나 ==로 끝나나요? 끝나야 하는데 그렇지 않다면 패딩이 제거된 것입니다.
  • data:로 시작하나요? 그렇다면 데이터 URI이며 쉼표 뒤의 부분만 Base64입니다.

1. 누락되었거나 잘못된 패딩

증상: Incorrect padding(Python), illegal base64 data at input byte N(Go), Invalid length for a Base-64 char array(.NET).

원인: 끝의 =가 제거되어 문자열 길이가 4의 배수가 아닙니다. JWT, URL, 일부 API에서는 흔한 일입니다.

해결: 디코딩 전에 빠진 패딩을 추가하세요. 필요한 =의 개수는 (4 - 길이 % 4) % 4입니다.

def fix_padding(s): return s + '=' * (-len(s) % 4)

유용한 점검법이 하나 있습니다. 유효한 Base64 문자열은 패딩 유무와 관계없이 길이를 4로 나눈 나머지가 1일 수 없습니다. 길이 % 4 == 1이라면 데이터가 잘렸거나 손상된 것이며, 패딩을 추가해도 고쳐지지 않습니다.

2. 표준 문자 집합과 URL 안전 문자 집합의 혼동

증상: Invalid character 또는 Illegal base64 character 2d(2d는 하이픈의 16진수 코드), 또는 오류 없이 디코딩되지만 결과가 잘못됨.

원인: Base64URL 문자열(-와 _ 포함)이 표준 디코더에 전달되었거나 그 반대입니다.

해결: 데이터에 맞는 디코더를 쓰거나, 먼저 문자를 변환하세요. URL 안전에서 표준으로 바꾸려면 -를 +로, _를 /로 치환합니다. 각각이 언제 쓰이는지는 Base64URL과 Base64의 차이를 참고하세요.

3. 더하기 기호가 공백으로 바뀜

증상: 디코딩된 데이터가 손상되거나 디코더가 공백 문자에 대해 불평하지만, URL이나 HTML 폼을 거쳐 온 값에서만 발생합니다.

원인: URL 쿼리 문자열과 폼 본문에서 +는 공백을 뜻합니다. 퍼센트 인코딩 없이 URL에 넣은 표준 Base64 값은 +가 공백으로 바뀐 채 도착합니다.

해결: 표준 Base64를 이스케이프 없이 URL에 넣지 마세요. 퍼센트 인코딩하거나(+는 %2B, /는 %2F, =는 %3D), 더 좋게는 Base64URL을 쓰세요. 수신 측에서 구제하려면 디코딩 전에 공백을 +로 바꾸세요.

4. 공백과 줄바꿈

증상: Java의 Illegal base64 character 20(공백)이나 0a(줄바꿈), .NET의 FormatException, 또는 긴 값에서만 실패.

원인: 값이 76자에서 줄바꿈되었거나, 이메일이나 PEM 파일에서 복사했거나, 끝에 줄바꿈이 있습니다.

해결: 디코딩 전에 공백을 제거하거나(Python의 re.sub(r'\s+', '', s), JavaScript의 s.replace(/\s+/g, '')), Java의 MIME 디코더처럼 공백을 허용하는 디코더를 쓰세요. 명령줄에서 인코딩할 때 echo가 추가하는 끝의 줄바꿈도 조심하세요.

5. 데이터 URI 접두사 포함

증상: 콜론이나 세미콜론을 언급하는 오류, 또는 <img src> 속성에서 복사한 것을 디코딩할 때 알아볼 수 없는 출력.

원인: 디코더가 iVBORw0...만이 아니라 data:image/png;base64,iVBORw0...를 받았습니다.

해결: 첫 번째 쉼표에서 나누고 두 번째 부분만 디코딩하세요: s.split(',', 1)[1]. 이미지만 필요하다면 접두사를 붙인 뒤 Base64 문자열을 그대로 src로 사용할 수도 있습니다. 저희 이미지 → Base64 변환기는 두 형태를 모두 만들어 줍니다.

6. 텍스트가 쓰레기 값이나 이상한 문자로 디코딩됨

증상: 디코딩은 성공하지만 텍스트에 Ã©, â€™, 물음표가 들어 있음.

원인: 문자 인코딩 불일치입니다. 바이트는 UTF-8인데 Latin-1이나 Windows-1252로 해석되었습니다. 반대도 일어납니다. UTF-16으로 인코딩된 텍스트(.NET의 Encoding.Unicode와 PowerShell의 -EncodedCommand 기본값)를 UTF-8로 디코딩하면 글자 사이에 널 문자가 보입니다.

해결: 양쪽이 텍스트 인코딩에 합의하도록 하고, 다른 이유가 없다면 UTF-8을 쓰세요. 디코딩된 데이터가 애초에 텍스트가 아니라면(이미지, PDF, 암호화된 블록) 문자열로 변환하지 말고 바이트로 유지하세요.

7. 이중 인코딩

증상: 디코딩했더니 또 다른 Base64처럼 보이는 문자열이 나오며, 흔히 ey나 SG로 시작합니다.

원인: 데이터가 두 번 인코딩되었습니다. 보통 코드의 한 계층과 라이브러리가 모두 Base64를 적용했기 때문입니다.

해결: 한 번 더 디코딩한 뒤, 근원에서 불필요한 인코딩 단계를 제거하세요. 간단한 확인법: 일반 텍스트의 진짜 Base64는 보통 글자로 시작하며, 결과 자체가 유효한 Base64라면 이중 인코딩의 강한 신호입니다.

8. 잘렸거나 손상된 데이터

증상: 특정 바이트 위치에서의 오류, 길이를 4로 나눈 나머지가 1, 일부만 열리는 파일.

원인: 열 수 제한, 로그 줄 길이 제한, URL 길이 제한, 또는 복사·붙여넣기 실수로 문자열이 잘렸습니다.

해결: 출발지와 목적지에서 문자열 길이를 비교하고, 그 사이 모든 시스템의 제한을 확인하세요. Base64에는 오류 검출 기능이 없으므로 무결성이 필요하다면 체크섬을 별도로 보내세요.

9. 잘못된 종류의 입력

증상: 해시, UUID, 16진수 문자열을 디코딩해서 읽을 수 없는 바이트를 받음.

원인: Base64처럼 보이는 모든 문자열이 Base64인 것은 아닙니다. 16진수 문자열과 일부 식별자는 Base64 문자 집합에도 존재하는 문자만 쓰므로, 디코더는 기꺼이 의미 없는 바이트로 디코딩합니다.

해결: 데이터를 만든 쪽에 형식을 확인하세요. 16진수는 0-9와 a-f만 쓰고 길이가 짝수입니다.

디버깅 체크리스트

  1. 정확한 문자열과 그 길이를 출력합니다.
  2. 문자 집합(+/ 또는 -_)을 파악합니다.
  3. 공백과 data: 접두사를 제거합니다.
  4. 길이가 4의 배수가 아니면 패딩을 복원합니다.
  5. 바이트로 디코딩한 다음에야 텍스트인지 판단합니다.
  6. 그래도 실패하면 decodeb64.com에 문자열을 붙여넣어 문제가 데이터인지 코드인지 확인하세요.

이 모든 실패를 설명하는 원리를 배우려면 Base64 인코딩이란 무엇이며 어떻게 동작할까?를 읽어 보세요. 언어별 자세한 내용은 JavaScript, Python, Java, C#, Go, PHP 가이드를 참고하세요.
