Base64・16進・Base32・Base85：どのエンコードを使うべきか

2026年11月読了時間約7分

バイナリデータをテキストとして表す必要があるとき、Base64が標準的な選択ですが、唯一の選択肢ではありません。16進数、Base32、Base58、Base85も同じ問題を解決しますが、サイズ、読みやすさ、堅牢性のトレードオフが異なります。選択を誤ると、ペイロードが膨らんだり、大文字小文字に起因するバグが起きたり、人間が正しく入力できない文字列になったりします。このガイドでは実測値でそれらを比較し、選び方のシンプルな目安を示します。

基本的な考え方：1文字あたりのビット数

バイト列をテキストにするエンコードは、1つの数値で決まります。出力の1文字が何ビット分のデータを運ぶか、です。文字セットが大きいほど1文字あたりのビット数が増え、出力は短くなります。

  • 16進（Base16）は16種類の記号なので、1文字は4ビットを運びます。
  • Base32は32種類の記号なので、1文字は5ビットを運びます。
  • Base64は64種類の記号なので、1文字は6ビットを運びます。
  • Base85は85種類の記号なので、1文字は平均して6.4ビット強を運びます。

文字セットが大きくなる代償として、句読点や大文字小文字の混在が増えます。そのため声に出して読んだり入力したりするのが難しくなり、大文字小文字を変えたり記号を特別扱いしたりするシステムによって壊されやすくなります。

実測したサイズ増加

公平に比較するため、1,000バイトのランダムデータをPythonの標準ライブラリでエンコードし、出力文字数を数えました。

  • 16進（Base16）：2,000文字（+100%）
  • Base32：1,600文字（+60%）
  • Base64：1,336文字（+33.6%）
  • Base85 / Ascii85：1,250文字（+25%）

Base58は2のべき乗の文字セットではないため、長さはデータによって変わりますが、実際にはBase64とBase32の中間に収まり、増加率は約37%です。

16進（Base16）

16進は各バイトを 0-9 と a-f の2文字で書きます。最も効率は悪いものの、最も読みやすい方式です。1バイトが常にちょうど2文字に対応し、個々のバイト値が見えるからです。

Hello → 48656c6c6f

向いている用途：ハッシュとチェックサム（SHA-256のダイジェストはほぼ常に16進で表示されます）、色、MACアドレス、デバッグ用ダンプ、人間がバイト単位で確認する必要があるものすべて。数字と英字だけを使うため、実際には大文字小文字や記号の問題とも無縁です。

Base32

Base32は英字 A-Z と数字 2-7 を使います。大文字小文字を区別しないシステムでも安全に使え、0とO、1とIのような紛らわしい文字を避けるよう設計されています。

Hello → JBSWY3DP

向いている用途：人が入力したり読み上げたりする値、および一部のファイルシステムやDNS名のように大文字小文字を区別しない場所に保存される値。最もよく知られた例は、認証アプリで2要素認証を設定するときに表示される秘密鍵です。出力は8文字の倍数になるよう = で埋められます。

Base64

Base64は A-Z、a-z、0-9、+、/ を使います。コンパクトさと普遍的なサポートのバランスが最も良い汎用の選択肢です。あらゆる言語に標準で備わっており、メール、データURI、JSON API、多くのプロトコルが期待する形式でもあります。

Hello → SGVsbG8=

向いている用途：JSON、XML、HTML、CSSへのファイル埋め込み、メールの添付ファイル、PEMファイル内の暗号鍵や証明書、バイナリデータを運ぶほとんどのAPI。URLセーフな変種であるBase64URLは、+ と / を - と _ に置き換えます。詳しくはBase64URLとBase64の違いをご覧ください。

Base58

Base58は、紛らわしい文字を取り除いたBase64です。0（ゼロ）、O（大文字のオー）、I（大文字のアイ）、l（小文字のエル）、および記号 + と / を含みません。句読点がないため、手で書き写しやすく、ほとんどのプログラムでダブルクリックで選択できる文字列になります。

向いている用途：暗号資産のアドレスや一部の短いIDなど、人が書き写す識別子。欠点は、2のべき乗の文字セットと違って、エンコードとデコードに大きな数の演算が必要になるため、速度が遅く、大きなデータには向かないことです。また、ほとんどの標準ライブラリには含まれていないので、通常はパッケージが必要です。

Base85（Ascii85）

Base85は4バイトを5文字にまとめ、ここで扱うテキストエンコードの中で最も小さい25%の増加に収まります。多くの記号を含む大きな文字セットを使うため、コンパクトですが、句読点が特別な意味を持つ場面では扱いにくくなります。

向いている用途：PDFやPostScriptのように、容量が重要で伝送経路を管理できる形式。Gitはバイナリパッチの埋め込みに変種を使っています。Pythonには base64.a85encode() と base64.b85encode() がありますが、他の言語での対応はBase64ほど普遍的ではありません。

選び方の簡単な目安

  • 人がバイトを読む（ハッシュ、デバッグ）？16進を使います。
  • 人が入力したり口頭で伝えたりする、または大文字小文字の変換に耐える必要がある？Base32を使います（大文字小文字が保たれるならBase58も可）。
  • 機械同士がテキストAPI、JSON、HTML、メールでバイナリデータをやり取りする？Base64を使います。
  • 値がURL、ファイル名、JWTに入る？Base64URLを使います。
  • 1バイトでも惜しく、両端を自分で管理できる？Base85を検討するか、むしろテキストエンコード自体をやめて生のバイトを送ります。

最良のエンコードは「使わない」こともある

上記のどのエンコードにもオーバーヘッドがあります。プロトコルが生のバイトを運べる場合、たとえば multipart/form-data によるバイナリアップロード、データベースのバイナリ列、gRPCなどでは、それを使いましょう。テキストエンコードは、通信経路にそれを強いられたときにだけ使います。
