Base64 到底大多少？体积与压缩实测

2026年11月阅读时间约 6 分钟

常见的说法是 Base64 会让数据大约增大 33%。这没错，但只说对了一部分，因为网络服务器会压缩响应，而压缩对 Base64 的影响在很大程度上取决于其中装的是什么。本文给出真实的测量结果，解释这些结果，并告诉你开销何时真的会让你付出代价。

测量方法

我用 Python 3 生成测试数据，用标准 base64 模块编码，并用最高压缩级别的 gzip 压缩。使用了两种输入：

  • 随机字节，其表现类似已经压缩或加密的数据：JPEG 和 PNG 图片、ZIP 文件、加密数据块。
  • 真实文本：本站首页 110,508 字节的 HTML 源码。

下面的数字来自 2026 年 11 月 12 日的那次运行。压缩后的确切字节数可能因工具和设置略有差异，但总体规律是稳定的。

结果 1：原始开销是 4/3

对于不同大小的随机数据，Base64 输出为：

  • 1,024 字节变为 1,368 字节（比值 1.336）
  • 10,240 字节变为 13,656 字节（比值 1.334）
  • 102,400 字节变为 136,536 字节（比值 1.333）
  • 1,048,576 字节（1 MB）变为 1,398,104 字节（比值 1.333）

比值恰好收敛于 4/3，即约 33.3%。小输入显示的略多一些，这是填充造成的：Base64 输出始终是四个字符的倍数，所以输入 1、2、3 个字节都会产生 4 个字符，而 4、5、6 个字节则产生 8 个字符。

结果 2：对随机数据，gzip 几乎完全抵消了开销

Base64 只使用 64 个不同的符号，所以每个字符在一个 8 位字节里只承载 6 位信息。好的压缩器能看出这种浪费并把它找回来。对于 1 MB 的样本：

  • 原始随机字节，压缩后：1,048,914 字节（基本没有变化，符合随机数据的预期）
  • 同样字节的 Base64：1,398,104 字节
  • Base64 再压缩：1,059,032 字节

经过 gzip 之后，Base64 版本仅比原始二进制大约大 1%。换句话说，如果你的服务器会压缩响应，那么对于 Base64 编码的图片和其他已压缩文件，33% 的代价在传输过程中基本消失了。Brotli 的表现与此类似。

有两点需要注意。第一，只有当 Base64 文本在传输中确实被压缩时才有帮助；未经压缩提供的 JSON API 或 HTML 页面要付出完整的 33%。第二，浏览器随后还得解压并解码数据，这会消耗普通二进制图片不需要的 CPU 时间。

结果 3：Base64 会损害文本的压缩

可压缩数据的表现则不同。对于 110,508 字节的 HTML 页面：

  • 原始：110,508 字节
  • Base64：147,344 字节（比值 1.333）
  • 原始，gzip 压缩后：27,294 字节（为原始的 24.7%）
  • Base64，gzip 压缩后：43,007 字节（为原始的 38.9%）

Base64 打乱了压缩器所依赖的模式。gzip 仍能大幅缩小编码后的文本，但结果比直接压缩原始文本大约 58%。如果可以选择，就把文本当作文本发送。

结果 4：换行会再增加一点

电子邮件中使用的 MIME 风格 Base64 每 76 个字符插入一个换行。对于 1000 个随机字节，普通 Base64 输出为 1,336 个字符，带换行的版本为 1,354 个字符，约多出 1.3%。这很少，但为 JSON、HTTP 头或数据 URI 生成 Base64 时，这是关闭换行的一个好理由。

开销何时重要

  • 未压缩的通道：不带 gzip 的 JSON API、消息队列、日志，以及存储 Base64 文本的数据库，要付出完整的 33%，外加编码和解码的 CPU 开销。
  • 内联图片：HTML 或 CSS 中的数据 URI 避免了一次请求，但无法单独缓存。一张 100 KB 的图片会增长到约 133 KB 的文本，每次页面变化都要重新下载。参见 Base64 数据 URI：何时内联图片。
  • 大文件：以 Base64 JSON 发送的 100 MB 上传，在未压缩时网络上约有 133 MB，并且在处理过程中需要在内存中多次保存。
  • 内存受限的客户端：移动设备和嵌入式环境更早感受到额外的内存分配。

开销何时无关紧要

  • 小的值：令牌、密钥、短标识符和几 KB 的图标都太小，开销根本不明显。
  • 对已压缩数据的压缩传输：如上所示，gzip 或 Brotli 抵消了大部分代价。
  • 一次性载荷：只编码一次、只使用一次的数据不会损失任何缓存。

实用规则

  1. 在通道允许的情况下，优先把二进制当作二进制发送（multipart 上传、二进制列、gRPC）。
  2. 如果必须在 HTTP 上使用 Base64，请在服务器上为相关内容类型启用 gzip 或 Brotli。
  3. 不要对本可作为文本发送的文本做 Base64 编码。
  4. 除非标准要求，否则关闭换行。
  5. 用你的真实数据测量：压缩率取决于内容。
