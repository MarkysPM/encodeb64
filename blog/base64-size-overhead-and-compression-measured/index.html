How Much Bigger Is Base64? Measured Size and Compression

November 20266 min read

The usual advice is that Base64 makes data about 33% bigger. That is true, but it is only part of the story, because web servers compress responses and the effect of compression on Base64 depends heavily on what is inside it. This article reports real measurements, explains the results, and tells you when the overhead actually costs you something.

How the Measurements Were Made

I generated test data with Python 3, encoded it with the standard base64 module and compressed it with gzip at the maximum compression level. Two kinds of input were used:

  • Random bytes, which behave like data that is already compressed or encrypted: JPEG and PNG images, ZIP files, encrypted blobs.
  • Real text: the 110,508-byte HTML source of this site’s home page.

The numbers below come from that run on 12 November 2026. Exact byte counts for compression can vary slightly between tools and settings, but the overall pattern is stable.

Result 1: The Raw Overhead Is 4/3

For random data of different sizes, the Base64 output is:

  • 1,024 bytes become 1,368 bytes (ratio 1.336)
  • 10,240 bytes become 13,656 bytes (ratio 1.334)
  • 102,400 bytes become 136,536 bytes (ratio 1.333)
  • 1,048,576 bytes (1 MB) become 1,398,104 bytes (ratio 1.333)

The ratio converges on exactly 4/3, which is about 33.3%. Small inputs show slightly more because of padding: Base64 output is always a multiple of four characters, so 1, 2 and 3 input bytes all produce 4 characters, while 4, 5 and 6 bytes all produce 8.

Result 2: Gzip Almost Fully Cancels the Overhead on Random Data

Base64 only uses 64 different symbols, so each character carries 6 bits of information in an 8-bit byte. A good compressor can see that wasted space and recover it. For the 1 MB sample:

  • Raw random bytes, compressed: 1,048,914 bytes (essentially no change, as expected for random data)
  • Base64 of the same bytes: 1,398,104 bytes
  • Base64, then compressed: 1,059,032 bytes

After gzip, the Base64 version is only about 1% larger than the original binary. In other words, if your server compresses the response, the 33% penalty for Base64-encoded images and other already-compressed files mostly disappears during transfer. Brotli behaves similarly.

Two caveats matter. First, this only helps if the Base64 text is actually compressed in transit; a JSON API or an HTML page served without compression pays the full 33%. Second, the browser then has to decompress and decode the data, which costs CPU time that a normal binary image does not.

Result 3: Base64 Hurts the Compression of Text

Compressible data behaves differently. For the 110,508-byte HTML page:

  • Original: 110,508 bytes
  • Base64: 147,344 bytes (ratio 1.333)
  • Original, gzipped: 27,294 bytes (24.7% of the original)
  • Base64, gzipped: 43,007 bytes (38.9% of the original)

Base64 scrambles the patterns that compressors use. Gzip can still shrink the encoded text a lot, but the result is about 58% larger than compressing the original text directly. If you have the choice, send text as text.

Result 4: Line Wrapping Adds a Little More

MIME-style Base64, used in email, inserts a line break every 76 characters. For 1,000 random bytes, the plain Base64 output was 1,336 characters and the line-wrapped version 1,354, which is about 1.3% more. It is small, but it is a good reason to disable wrapping when producing Base64 for JSON, HTTP headers or data URIs.

When the Overhead Matters

  • Uncompressed channels: JSON APIs without gzip, message queues, logs and databases storing Base64 text pay the full 33%, plus the CPU cost of encoding and decoding.
  • Inlined images: a data URI inside HTML or CSS avoids a request but cannot be cached separately. A 100 KB image grows to about 133 KB of text, downloaded again whenever the page changes. See Base64 Data URIs: When to Inline Images.
  • Large files: a 100 MB upload sent as Base64 JSON is about 133 MB on the wire without compression and must be held in memory several times during processing.
  • Memory-constrained clients: mobile and embedded environments feel the extra allocation sooner.

When It Does Not Matter

  • Small values: tokens, keys, short identifiers and icons of a few kilobytes are too small for the overhead to be noticeable.
  • Compressed transport of already-compressed data: as shown above, gzip or Brotli cancels most of the penalty.
  • Single-use payloads: data that is encoded once and consumed once has no cache to lose.

Practical Rules

  1. Prefer sending binary as binary (multipart uploads, binary columns, gRPC) when the channel allows it.
  2. If you must use Base64 over HTTP, enable gzip or Brotli on the server for the relevant content types.
  3. Do not Base64-encode text that you could send as text.
  4. Turn off line wrapping unless a standard requires it.
  5. Measure with your real data: compression ratios depend on the content.
