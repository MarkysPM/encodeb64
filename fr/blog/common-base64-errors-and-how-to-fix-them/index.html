Erreurs Base64 courantes et comment les corriger

Novembre 20268 min de lecture

Base64 est simple, et pourtant il produit certains des messages d'erreur les plus déroutants de la programmation : Incorrect padding, Invalid character, The input is not a valid Base-64 string. Les messages varient selon le langage, mais les causes sont presque toujours les mêmes. Ce guide les énumère dans l'ordre où il faut les vérifier, avec le symptôme, la cause et la solution de chacune.

Première étape : regarder la chaîne

Avant de modifier le code, regardez la chaîne que vous essayez de décoder. Quatre vérifications rapides répondent à la plupart des questions :

  • Contient-elle - ou _ ? Alors c'est du Base64URL, pas du Base64 standard.
  • Contient-elle + ou / ? Alors c'est du Base64 standard.
  • Se termine-t-elle par = ou == ? Si elle le devrait et ne le fait pas, le remplissage a été retiré.
  • Commence-t-elle par data: ? Alors c'est une URI de données et seule la partie après la virgule est du Base64.

1. Remplissage manquant ou incorrect

Symptômes : Incorrect padding (Python), illegal base64 data at input byte N (Go), Invalid length for a Base-64 char array (.NET).

Cause : la longueur de la chaîne n'est pas un multiple de quatre parce que les = finaux ont été supprimés, ce qui est normal dans les JWT, les URL et certaines API.

Solution : ajoutez le remplissage manquant avant de décoder. Le nombre de = nécessaires est (4 - longueur % 4) % 4 :

def fix_padding(s): return s + '=' * (-len(s) % 4)

Un contrôle utile : une chaîne Base64 valide, avec ou sans remplissage, ne peut jamais avoir une longueur égale à 1 modulo 4. Si longueur % 4 == 1, les données sont tronquées ou corrompues et aucun remplissage n'y changera rien.

2. Confusion entre alphabet standard et alphabet sûr pour les URL

Symptômes : Invalid character ou Illegal base64 character 2d (où 2d est le code hexadécimal d'un tiret), ou une sortie qui se décode sans erreur mais qui est fausse.

Cause : une chaîne Base64URL (avec - et _) a été donnée à un décodeur standard, ou l'inverse.

Solution : utilisez le décodeur qui correspond aux données, ou traduisez d'abord les caractères : remplacez - par + et _ par / pour passer du format sûr pour les URL au format standard. Voir Base64URL vs Base64 pour savoir quand utiliser chacun.

3. Plus transformés en espaces

Symptômes : les données décodées sont corrompues, ou le décodeur se plaint d'une espace, mais seulement pour les valeurs qui ont transité par une URL ou un formulaire HTML.

Cause : dans les chaînes de requête d'URL et les corps de formulaire, un + signifie une espace. Une valeur Base64 standard placée dans une URL sans encodage pour-cent arrive avec ses + remplacés par des espaces.

Solution : ne mettez jamais du Base64 standard dans une URL sans l'échapper. Soit vous l'encodez en pourcentage (+ devient %2B, / devient %2F, = devient %3D), soit, mieux, vous utilisez Base64URL. En secours côté réception, remplacez les espaces par + avant de décoder.

4. Espaces blancs et sauts de ligne

Symptômes : Illegal base64 character 20 (espace) ou 0a (saut de ligne) en Java, FormatException en .NET, ou un échec uniquement sur les valeurs longues.

Cause : la valeur a été coupée à 76 caractères, copiée depuis un e-mail ou un fichier PEM, ou se termine par un saut de ligne.

Solution : supprimez les espaces blancs avant de décoder (re.sub(r'\s+', '', s) en Python, s.replace(/\s+/g, '') en JavaScript), ou utilisez un décodeur qui les tolère, comme le décodeur MIME de Java. Méfiez-vous aussi du saut de ligne final ajouté par echo lorsque vous encodez en ligne de commande.

5. Inclure le préfixe de l'URI de données

Symptômes : une erreur mentionnant les deux-points ou le point-virgule, ou une sortie illisible en décodant quelque chose copié depuis un attribut <img src>.

Cause : le décodeur a reçu data:image/png;base64,iVBORw0... au lieu de seulement iVBORw0....

Solution : séparez à la première virgule et ne décodez que la seconde partie : s.split(',', 1)[1]. Si vous n'avez besoin que de l'image, vous pouvez aussi utiliser directement la chaîne Base64 comme src après avoir ajouté le préfixe. Notre convertisseur d'image en Base64 produit les deux formes.

6. Le texte décodé est du charabia ou contient des caractères étranges

Symptômes : le décodage réussit mais le texte contient Ã©, â€™ ou des points d'interrogation.

Cause : une incompatibilité d'encodage de caractères. Les octets sont de l'UTF-8, mais ils ont été interprétés comme du Latin-1 ou du Windows-1252. L'inverse existe aussi : un texte encodé en UTF-16 (la valeur par défaut de Encoding.Unicode en .NET et de -EncodedCommand dans PowerShell) décodé en UTF-8 montre des caractères nuls entre les lettres.

Solution : faites en sorte que les deux côtés s'accordent sur l'encodage du texte, et utilisez l'UTF-8 sauf raison contraire. Si les données décodées ne sont pas du texte (une image, un PDF, un bloc chiffré), ne les convertissez pas en chaîne ; gardez-les en octets.

7. Double encodage

Symptômes : après décodage, vous obtenez une autre chaîne qui ressemble à du Base64, commençant souvent par ey ou SG.

Cause : les données ont été encodées deux fois, généralement parce qu'une couche de votre code et une bibliothèque ont toutes deux appliqué Base64.

Solution : décodez une seconde fois, puis supprimez l'étape d'encodage en trop à la source. Un test rapide : le vrai Base64 d'un texte ordinaire commence généralement par une lettre, et un résultat qui est lui-même du Base64 valide est un fort indice de double encodage.

8. Données tronquées ou corrompues

Symptômes : une erreur à une position d'octet précise, une longueur égale à 1 modulo 4, ou un fichier qui ne s'ouvre qu'en partie.

Cause : la chaîne a été coupée par une limite de colonnes, une limite de ligne de journal, une limite de longueur d'URL ou une erreur de copier-coller.

Solution : comparez la longueur de la chaîne à la source et à la destination, et vérifiez les limites de chaque système intermédiaire. Base64 n'a aucune détection d'erreur : si vous avez besoin d'intégrité, envoyez une somme de contrôle séparément.

9. Le mauvais type d'entrée

Symptômes : décoder une empreinte, un UUID ou une chaîne hex et recevoir des octets illisibles.

Cause : toute chaîne qui ressemble à du Base64 n'en est pas. Les chaînes hex et certains identifiants n'utilisent que des caractères qui existent aussi dans l'alphabet Base64, si bien qu'un décodeur les décodera volontiers en octets sans signification.

Solution : confirmez le format auprès de la personne qui a produit les données. L'hex n'utilise que 0-9 et a-f et a une longueur paire.

Une liste de contrôle pour le débogage

  1. Affichez la chaîne exacte et sa longueur.
  2. Identifiez l'alphabet (+/ ou -_).
  3. Supprimez les espaces blancs et tout préfixe data:.
  4. Rétablissez le remplissage si la longueur n'est pas un multiple de quatre.
  5. Décodez en octets et ne décidez qu'ensuite s'il s'agit de texte.
  6. Si cela échoue toujours, collez la chaîne sur decodeb64.com pour savoir si le problème vient des données ou de votre code.
