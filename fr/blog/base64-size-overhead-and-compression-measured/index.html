De combien Base64 est-il plus gros ? Taille et compression

Novembre 20266 min de lecture

Le conseil habituel est que Base64 rend les données environ 33 % plus grosses. C'est vrai, mais ce n'est qu'une partie de l'histoire, car les serveurs web compressent les réponses et l'effet de la compression sur Base64 dépend beaucoup de ce qu'il contient. Cet article présente des mesures réelles, explique les résultats et vous dit quand le surcoût vous coûte vraiment quelque chose.

Comment les mesures ont été faites

J'ai généré des données de test avec Python 3, les ai encodées avec le module standard base64 et compressées avec gzip au niveau de compression maximal. Deux types d'entrée ont été utilisés :

  • Des octets aléatoires, qui se comportent comme des données déjà compressées ou chiffrées : images JPEG et PNG, fichiers ZIP, blocs chiffrés.
  • Du texte réel : les 110 508 octets du code source HTML de la page d'accueil de ce site.

Les chiffres ci-dessous proviennent de cette exécution du 12 novembre 2026. Les tailles exactes de compression peuvent varier légèrement selon les outils et les réglages, mais le schéma général est stable.

Résultat 1 : le surcoût brut est de 4/3

Pour des données aléatoires de différentes tailles, la sortie Base64 est :

  • 1 024 octets deviennent 1 368 octets (rapport 1,336)
  • 10 240 octets deviennent 13 656 octets (rapport 1,334)
  • 102 400 octets deviennent 136 536 octets (rapport 1,333)
  • 1 048 576 octets (1 Mo) deviennent 1 398 104 octets (rapport 1,333)

Le rapport converge exactement vers 4/3, soit environ 33,3 %. Les petites entrées montrent un peu plus à cause du remplissage : la sortie Base64 est toujours un multiple de quatre caractères, donc 1, 2 et 3 octets d'entrée produisent 4 caractères, tandis que 4, 5 et 6 octets en produisent 8.

Résultat 2 : gzip annule presque tout le surcoût sur des données aléatoires

Base64 n'utilise que 64 symboles différents, donc chaque caractère porte 6 bits d'information dans un octet de 8 bits. Un bon compresseur voit cet espace gaspillé et le récupère. Pour l'échantillon de 1 Mo :

  • Octets aléatoires bruts, compressés : 1 048 914 octets (pratiquement aucun changement, comme prévu pour des données aléatoires)
  • Base64 des mêmes octets : 1 398 104 octets
  • Base64, puis compressé : 1 059 032 octets

Après gzip, la version Base64 n'est qu'environ 1 % plus grosse que le binaire d'origine. Autrement dit, si votre serveur compresse la réponse, la pénalité de 33 % pour les images et autres fichiers déjà compressés encodés en Base64 disparaît en grande partie pendant le transfert. Brotli se comporte de façon similaire.

Deux réserves comptent. D'abord, cela n'aide que si le texte Base64 est réellement compressé en transit ; une API JSON ou une page HTML servie sans compression paie les 33 % complets. Ensuite, le navigateur doit décompresser et décoder les données, ce qui coûte du temps processeur qu'une image binaire normale n'exige pas.

Résultat 3 : Base64 nuit à la compression du texte

Les données compressibles se comportent différemment. Pour la page HTML de 110 508 octets :

  • Original : 110 508 octets
  • Base64 : 147 344 octets (rapport 1,333)
  • Original, compressé avec gzip : 27 294 octets (24,7 % de l'original)
  • Base64, compressé avec gzip : 43 007 octets (38,9 % de l'original)

Base64 brouille les motifs qu'exploitent les compresseurs. Gzip peut encore beaucoup réduire le texte encodé, mais le résultat est environ 58 % plus gros que la compression directe du texte d'origine. Si vous avez le choix, envoyez le texte comme texte.

Résultat 4 : le retour à la ligne ajoute un peu plus

Le Base64 de style MIME, utilisé dans le courrier électronique, insère un saut de ligne tous les 76 caractères. Pour 1 000 octets aléatoires, la sortie Base64 simple faisait 1 336 caractères et la version avec retours à la ligne 1 354, soit environ 1,3 % de plus. C'est peu, mais c'est une bonne raison de désactiver le retour à la ligne quand on produit du Base64 pour du JSON, des en-têtes HTTP ou des URI de données.

Quand le surcoût compte

  • Canaux non compressés : les API JSON sans gzip, les files de messages, les journaux et les bases de données qui stockent du texte Base64 paient les 33 % complets, plus le coût processeur de l'encodage et du décodage.
  • Images intégrées : une URI de données dans du HTML ou du CSS évite une requête mais ne peut pas être mise en cache séparément. Une image de 100 Ko grossit jusqu'à environ 133 Ko de texte, téléchargés à nouveau chaque fois que la page change. Voir URI de données Base64 : quand intégrer des images.
  • Gros fichiers : un envoi de 100 Mo transmis en JSON Base64 représente environ 133 Mo sur le réseau sans compression et doit être gardé en mémoire plusieurs fois pendant le traitement.
  • Clients à mémoire limitée : les mobiles et les environnements embarqués ressentent plus tôt l'allocation supplémentaire.

Quand cela n'a pas d'importance

  • Petites valeurs : jetons, clés, identifiants courts et icônes de quelques kilooctets sont trop petits pour que le surcoût se remarque.
  • Transport compressé de données déjà compressées : comme montré plus haut, gzip ou Brotli annulent l'essentiel de la pénalité.
  • Charges à usage unique : des données encodées une fois et consommées une fois ne perdent aucun cache.

Règles pratiques

  1. Préférez envoyer le binaire comme binaire (envois multipart, colonnes binaires, gRPC) quand le canal le permet.
  2. Si vous devez utiliser Base64 sur HTTP, activez gzip ou Brotli sur le serveur pour les types de contenu concernés.
  3. N'encodez pas en Base64 du texte que vous pourriez envoyer comme texte.
  4. Désactivez le retour à la ligne sauf si une norme l'exige.
  5. Mesurez avec vos données réelles : les taux de compression dépendent du contenu.

Pour obtenir les tailles exactes de vos propres fichiers, utilisez le convertisseur d'image en Base64 ou l'encodeur de la page d'accueil et comparez avec la taille d'origine.
