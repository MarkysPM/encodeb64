Ist Base64 sicher? Kodierung vs. Verschlüsselung

November 20267 Min. Lesezeit

Ein Base64-String wie cGFzc3dvcmQxMjM= sieht verschlüsselt aus, und dieser Eindruck verleitet viele dazu, ihn als Schutz zu betrachten. Das ist er nicht. Base64 ist eine umkehrbare Kodierung ohne Schlüssel und ohne Geheimnis, und jeder kann sie in einer Sekunde dekodieren. Dieser Leitfaden erklärt den Unterschied zwischen Kodierung und Verschlüsselung, zeigt, wo Base64 häufig mit Sicherheit verwechselt wird, und gibt praktische Regeln für den Umgang mit Geheimnissen und nicht vertrauenswürdigen Eingaben.

Kodierung ist keine Verschlüsselung

Die beiden Konzepte lösen verschiedene Probleme:

  • Kodierung ändert die Darstellung von Daten, damit sie einen bestimmten Kanal passieren können. Das Verfahren ist öffentlich, es gibt keinen Schlüssel, und jeder kann sie umkehren. Base64, URL-Kodierung und Hex sind Kodierungen.
  • Verschlüsselung wandelt Daten so um, dass nur jemand mit dem richtigen Schlüssel sie lesen kann. Selbst wenn das Verfahren öffentlich ist, wie bei AES, bleiben die Daten ohne Schlüssel unlesbar.
  • Hashing erzeugt einen Fingerabdruck fester Größe, der sich nicht umkehren lässt. Er dient Integritätsprüfungen und der Passwortspeicherung (mit einer geeigneten Passwort-Hashfunktion).

Der obige String dekodiert mit jedem Base64-Dekodierer zu password123. Nichts an der Umwandlung hängt von einem Geheimnis ab.

Wo Base64 mit Sicherheit verwechselt wird

HTTP Basic Authentication

Basic-Authentifizierung sendet Authorization: Basic gefolgt vom Base64 von Benutzername:Passwort. Das Base64 dient nur dazu, dass Sonderzeichen in einem Header überleben. Jeder, der die Anfrage sehen kann, kann die Zugangsdaten lesen, weshalb Basic-Authentifizierung nur über HTTPS verwendet werden darf.

JSON Web Tokens

Header und Payload eines JWT sind Base64URL-kodiert, nicht verschlüsselt. Jeder, der das Token besitzt, kann alle darin enthaltenen Claims lesen. Die Signatur beweist nur, dass das Token nicht verändert wurde; den Inhalt verbirgt sie nicht. Legen Sie keine Geheimnisse oder sensiblen personenbezogenen Daten in einem normalen signierten JWT ab. Mehr dazu in Wie JWT-Tokens die Base64URL-Kodierung verwenden.

Kubernetes Secrets

Werte in einem Kubernetes-Secret-Manifest sind Base64-kodiert. Das ist eine Formatanforderung für die binärsichere Speicherung, kein Schutz. Standardmäßig werden Secrets unverschlüsselt im Datenspeicher des Clusters abgelegt, geschützt werden sie also durch Zugriffskontrolle und optionale Verschlüsselung im Ruhezustand. Behandeln Sie die Manifestdatei als sensibel und halten Sie sie aus der Versionsverwaltung heraus.

Konfigurationsdateien und Umgebungsvariablen

Ein Passwort als Base64 in einer Konfigurationsdatei, einer Docker-Umgebungsvariable oder einer mobilen App zu speichern, fügt für Angreifer nur einen Dekodierschritt hinzu. Alles, was in einer Client-Anwendung ausgeliefert wird, kann extrahiert und dekodiert werden.

Verschleierung durch Angreifer

Schadskripte verstecken Befehle oft in Base64, damit beiläufige Prüfung oder einfache Zeichenkettensuche sie übersieht. Die Option -EncodedCommand von PowerShell, die Base64 von UTF-16-Text erwartet, ist ein bekanntes Beispiel. Für Verteidiger bedeutet das: Unerwartetes Base64 in Logs und Skripten verdient einen genaueren Blick – dekodieren und lesen Sie es.

Geheimnisse richtig schützen

  • Nutzen Sie Verschlüsselung mit einem modernen authentifizierten Algorithmus wie AES-GCM oder ChaCha20-Poly1305 aus einer gut geprüften Bibliothek. Erfinden Sie kein eigenes Verfahren.
  • Halten Sie Schlüssel getrennt von den Daten und verwalten Sie sie in einem Secrets-Manager oder Schlüsselverwaltungsdienst statt in Code oder Konfiguration.
  • Hashen Sie Passwörter mit einem dafür vorgesehenen Algorithmus wie Argon2id, scrypt oder bcrypt. Speichern Sie sie niemals so kodiert oder verschlüsselt, dass sie umkehrbar sind.
  • Nutzen Sie überall HTTPS, damit Zugangsdaten und Tokens bei der Übertragung verschlüsselt sind.
  • Kodieren Sie nach dem Verschlüsseln, und nur wenn der Kanal Text braucht. Die Reihenfolge lautet: erst verschlüsseln, dann den Chiffretext in Base64 umwandeln.

Sicherheitsrisiken beim Verarbeiten von Base64-Eingaben

Auch wenn Base64 selbst keinen Schutz bietet, gibt es echte Sicherheitsaspekte, wenn Ihre Anwendung Base64 von außen annimmt:

  • Größenlimits. Eine kleine Anfrage kann zu einem großen Puffer dekodieren. Begrenzen Sie die Länge eingehenden Base64s vor dem Dekodieren, um Speichererschöpfung zu vermeiden.
  • Dekodierten Inhalt prüfen. Eine dekodierte Datei kann alles sein, unabhängig vom angegebenen Typ. Prüfen Sie den tatsächlichen Dateityp und scannen Sie Uploads wie jede andere Datei.
  • Dekodierten Daten nicht vertrauen. Wird ein dekodierter Wert in einer Datenbankabfrage, einem Befehl oder in HTML verwendet, wenden Sie die üblichen Schutzmaßnahmen an: parametrisierte Abfragen, Escaping und Ausgabekodierung.
  • Vorsicht bei Data-URIs. Fügen Sie nie vom Benutzer gelieferte Data-URIs ungeprüft in Links oder Frames ein und beschränken Sie sie in Ihrer Content Security Policy auf die Stellen, an denen Sie sie brauchen, etwa img-src.
  • Striktes Dekodieren. Weisen Sie Eingaben mit Zeichen außerhalb des Alphabets ab, statt sie zu ignorieren, damit verschiedene Komponenten denselben String nicht unterschiedlich interpretieren.

Wann Base64 in Ordnung ist

Nichts davon bedeutet, dass Base64 schlecht ist. Es ist genau das richtige Werkzeug für seine Aufgabe: Binärdaten über Textkanäle zu transportieren. Der Fehler ist, ihm eine Aufgabe aufzubürden, für die es nie gedacht war. Sind die Daten nicht geheim, genügt Base64 allein. Sind sie geheim, verschlüsseln Sie sie und verwenden Base64 nur für den Transport des Chiffretexts.
