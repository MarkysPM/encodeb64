Base64는 얼마나 더 커질까? 크기와 압축 실측

2026년 11월읽는 시간 약 6분

Base64는 데이터를 약 33% 크게 만든다는 말을 흔히 합니다. 사실이지만 이야기의 일부에 불과합니다. 웹 서버는 응답을 압축하고, 압축이 Base64에 미치는 영향은 안에 무엇이 들어 있느냐에 크게 좌우되기 때문입니다. 이 글은 실제 측정 결과를 제시하고, 결과를 설명하며, 오버헤드가 실제로 비용이 되는 때를 알려 줍니다.

측정 방법

Python 3으로 테스트 데이터를 만들고, 표준 base64 모듈로 인코딩한 다음, 최대 압축 수준의 gzip으로 압축했습니다. 두 종류의 입력을 사용했습니다.

  • 무작위 바이트: 이미 압축되었거나 암호화된 데이터처럼 동작합니다. JPEG와 PNG 이미지, ZIP 파일, 암호화된 블록 등입니다.
  • 실제 텍스트: 이 사이트 홈 페이지의 110,508바이트짜리 HTML 소스.

아래 수치는 2026년 11월 12일의 이 실행에서 나온 것입니다. 압축 후 정확한 바이트 수는 도구와 설정에 따라 조금씩 다를 수 있지만, 전체적인 경향은 안정적입니다.

결과 1: 기본 오버헤드는 4/3

크기가 다른 무작위 데이터에 대한 Base64 출력은 다음과 같습니다.

  • 1,024바이트 → 1,368바이트 (비율 1.336)
  • 10,240바이트 → 13,656바이트 (비율 1.334)
  • 102,400바이트 → 136,536바이트 (비율 1.333)
  • 1,048,576바이트(1 MB) → 1,398,104바이트 (비율 1.333)

비율은 정확히 4/3, 즉 약 33.3%로 수렴합니다. 작은 입력은 패딩 때문에 약간 더 크게 나옵니다. Base64 출력은 항상 4자의 배수이므로, 입력이 1, 2, 3바이트면 모두 4자가 되고 4, 5, 6바이트면 8자가 됩니다.

결과 2: 무작위 데이터에서는 gzip이 오버헤드를 거의 완전히 상쇄

Base64는 64가지 기호만 사용하므로, 한 글자가 8비트 바이트 안에 6비트의 정보만 담습니다. 좋은 압축기는 이 낭비되는 공간을 알아보고 되찾습니다. 1 MB 샘플의 결과는 다음과 같습니다.

  • 원시 무작위 바이트를 압축: 1,048,914바이트 (무작위 데이터이므로 예상대로 거의 변화 없음)
  • 같은 바이트의 Base64: 1,398,104바이트
  • Base64로 바꾼 뒤 압축: 1,059,032바이트

gzip 이후 Base64 버전은 원래 바이너리보다 약 1%만 클 뿐입니다. 다시 말해, 서버가 응답을 압축한다면 Base64로 인코딩된 이미지와 기타 이미 압축된 파일에 대한 33% 손해는 전송 중에 대부분 사라집니다. Brotli도 비슷하게 동작합니다.

두 가지 단서가 중요합니다. 첫째, Base64 텍스트가 전송 중에 실제로 압축될 때만 도움이 됩니다. 압축 없이 제공되는 JSON API나 HTML 페이지는 33%를 그대로 부담합니다. 둘째, 브라우저는 이후 데이터를 압축 해제하고 디코딩해야 하며, 이는 일반 바이너리 이미지에는 없는 CPU 시간이 듭니다.

결과 3: Base64는 텍스트의 압축 효율을 떨어뜨린다

압축이 잘되는 데이터는 다르게 동작합니다. 110,508바이트짜리 HTML 페이지의 경우:

  • 원본: 110,508바이트
  • Base64: 147,344바이트 (비율 1.333)
  • 원본을 gzip으로 압축: 27,294바이트 (원본의 24.7%)
  • Base64를 gzip으로 압축: 43,007바이트 (원본의 38.9%)

Base64는 압축기가 이용하는 패턴을 흐트러뜨립니다. gzip은 인코딩된 텍스트도 상당히 줄일 수 있지만, 결과는 원본 텍스트를 직접 압축한 것보다 약 58% 큽니다. 선택할 수 있다면 텍스트는 텍스트로 보내세요.

결과 4: 줄 바꿈이 조금 더 보탠다

이메일에서 쓰는 MIME 방식의 Base64는 76자마다 줄바꿈을 넣습니다. 무작위 바이트 1,000개에서 일반 Base64 출력은 1,336자였고 줄바꿈 버전은 1,354자로 약 1.3% 더 많았습니다. 작은 차이지만, JSON, HTTP 헤더, 데이터 URI용으로 Base64를 만들 때는 줄바꿈을 끄는 좋은 이유가 됩니다.

오버헤드가 문제 되는 경우

  • 압축되지 않는 채널: gzip 없는 JSON API, 메시지 큐, 로그, Base64 텍스트를 저장하는 데이터베이스는 33%를 그대로 부담하고, 인코딩·디코딩의 CPU 비용도 듭니다.
  • 인라인 이미지: HTML이나 CSS 안의 데이터 URI는 요청 하나를 줄이지만 별도로 캐시할 수 없습니다. 100 KB 이미지는 약 133 KB의 텍스트가 되어 페이지가 바뀔 때마다 다시 내려받습니다. Base64 데이터 URI: 이미지를 인라인으로 넣을 때를 참고하세요.
  • 큰 파일: Base64 JSON으로 보내는 100 MB 업로드는 압축이 없으면 네트워크에서 약 133 MB가 되고, 처리 중에 메모리에 여러 번 올라가야 합니다.
  • 메모리가 제한된 클라이언트: 모바일과 임베디드 환경은 추가 할당을 더 빨리 체감합니다.

문제 되지 않는 경우

  • 작은 값: 토큰, 키, 짧은 식별자, 몇 킬로바이트짜리 아이콘은 오버헤드가 눈에 띌 만큼 크지 않습니다.
  • 이미 압축된 데이터의 압축 전송: 위에서 보았듯 gzip이나 Brotli가 손해의 대부분을 상쇄합니다.
  • 일회성 페이로드: 한 번 인코딩되어 한 번 사용되는 데이터는 잃을 캐시가 없습니다.

실용적인 규칙

  1. 채널이 허용한다면 바이너리는 바이너리로 보내세요(멀티파트 업로드, 바이너리 열, gRPC).
  2. HTTP에서 Base64를 꼭 써야 한다면, 관련 콘텐츠 유형에 대해 서버에서 gzip이나 Brotli를 켜세요.
  3. 텍스트로 보낼 수 있는 텍스트를 Base64로 인코딩하지 마세요.
  4. 표준이 요구하지 않는 한 줄바꿈을 끄세요.
  5. 실제 데이터로 측정하세요. 압축률은 내용에 따라 다릅니다.

자신의 파일에 대한 정확한 크기를 알려면 이미지 → Base64 변환기나 홈 페이지의 인코더를 사용해 원본 파일 크기와 비교하세요. 4/3 비율의 원리는 Base64 인코딩이란 무엇이며 어떻게 동작할까?에서, 오버헤드가 다른 대안은 Base64 vs 16진수 vs Base32 vs Base85: 무엇을 쓸까?에서 확인하세요.
