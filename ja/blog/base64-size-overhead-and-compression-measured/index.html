Base64はどれだけ大きくなる？サイズと圧縮の実測

2026年11月読了時間約6分

Base64はデータを約33%大きくする、とよく言われます。それは事実ですが、話の一部にすぎません。Webサーバーはレスポンスを圧縮し、Base64への圧縮の効果は中身に大きく左右されるからです。この記事では実際の測定結果を示し、その結果を説明し、オーバーヘッドが実際にコストになるのはいつかをお伝えします。

測定方法

Python 3でテストデータを生成し、標準の base64 モジュールでエンコードし、最大圧縮レベルの gzip で圧縮しました。入力は2種類です。

  • ランダムなバイト列：すでに圧縮または暗号化されたデータのように振る舞います。JPEGやPNGの画像、ZIPファイル、暗号化されたブロックなどです。
  • 実際のテキスト：このサイトのトップページの、110,508バイトのHTMLソース。

以下の数値は、2026年11月12日のこの実行によるものです。圧縮後の正確なバイト数はツールや設定によって多少変わることがありますが、全体の傾向は安定しています。

結果1：素のオーバーヘッドは4/3

サイズの異なるランダムデータに対するBase64の出力は次のとおりです。

  • 1,024バイト → 1,368バイト（比率 1.336）
  • 10,240バイト → 13,656バイト（比率 1.334）
  • 102,400バイト → 136,536バイト（比率 1.333）
  • 1,048,576バイト（1 MB）→ 1,398,104バイト（比率 1.333）

比率はちょうど4/3、つまり約33.3%に収束します。小さな入力では、パディングのためにわずかに大きく見えます。Base64の出力は常に4文字の倍数なので、入力が1、2、3バイトならすべて4文字、4、5、6バイトなら8文字になります。

結果2：ランダムデータではgzipがオーバーヘッドをほぼ打ち消す

Base64は64種類の記号しか使わないため、1文字が8ビットのバイトの中で6ビットの情報しか運びません。優れた圧縮器はこの無駄な領域を見つけて取り戻します。1 MBのサンプルでは次のようになりました。

  • 生のランダムバイトを圧縮：1,048,914バイト（ランダムデータなので予想どおり、ほぼ変化なし）
  • 同じバイト列のBase64：1,398,104バイト
  • Base64にしてから圧縮：1,059,032バイト

gzip後のBase64版は、元のバイナリより約1%大きいだけです。言い換えれば、サーバーがレスポンスを圧縮していれば、Base64でエンコードされた画像などの圧縮済みファイルに対する33%のペナルティは、転送中にほとんど消えます。Brotliも同様に振る舞います。

2つ注意点があります。1つ目は、Base64テキストが転送中に実際に圧縮される場合にのみ効果があることです。圧縮なしで配信されるJSON APIやHTMLページは、33%をそのまま支払います。2つ目は、その後ブラウザがデータを展開してデコードする必要があり、通常のバイナリ画像にはないCPU時間がかかることです。

結果3：Base64はテキストの圧縮を悪化させる

圧縮しやすいデータでは挙動が異なります。110,508バイトのHTMLページでは次のとおりです。

  • 元のデータ：110,508バイト
  • Base64：147,344バイト（比率 1.333）
  • 元のデータをgzip圧縮：27,294バイト（元の24.7%）
  • Base64をgzip圧縮：43,007バイト（元の38.9%）

Base64は、圧縮器が利用するパターンを崩します。gzipはエンコードされたテキストでもかなり縮められますが、元のテキストを直接圧縮した場合より約58%大きくなります。選べるなら、テキストはテキストのまま送りましょう。

結果4：行の折り返しでさらに少し増える

メールで使われるMIME形式のBase64は、76文字ごとに改行を入れます。1,000バイトのランダムデータでは、通常のBase64出力が1,336文字、折り返し版が1,354文字で、約1.3%の増加でした。わずかですが、JSON、HTTPヘッダー、データURI向けにBase64を作るときは折り返しを無効にする十分な理由になります。

オーバーヘッドが問題になるとき

  • 圧縮されない通信経路：gzipなしのJSON API、メッセージキュー、ログ、Base64テキストを保存するデータベースは、33%をそのまま負担し、さらにエンコード・デコードのCPUコストもかかります。
  • インライン画像：HTMLやCSS内のデータURIはリクエストを省けますが、個別にキャッシュできません。100 KBの画像は約133 KBのテキストになり、ページが変わるたびに再ダウンロードされます。Base64データURI：画像をインライン化するタイミングをご覧ください。
  • 大きなファイル：Base64のJSONで送られる100 MBのアップロードは、圧縮なしではネットワーク上で約133 MBになり、処理中に何度もメモリに保持される必要があります。
  • メモリが限られたクライアント：モバイルや組み込み環境では、追加のメモリ確保の影響を早く受けます。

問題にならないとき

  • 小さな値：トークン、鍵、短い識別子、数キロバイトのアイコンは、オーバーヘッドが目立つには小さすぎます。
  • 圧縮済みデータの圧縮転送：上で示したように、gzipやBrotliがペナルティの大半を打ち消します。
  • 使い捨てのペイロード：一度エンコードされて一度だけ使われるデータは、失うキャッシュがありません。

実用的なルール

  1. 通信経路が許すなら、バイナリはバイナリのまま送りましょう（マルチパートアップロード、バイナリ列、gRPC）。
  2. HTTPでBase64を使わざるを得ない場合は、該当するコンテンツタイプについてサーバーでgzipまたはBrotliを有効にします。
  3. テキストとして送れるテキストをBase64でエンコードしないでください。
  4. 標準で要求されない限り、行の折り返しは無効にします。
  5. 実際のデータで測定しましょう。圧縮率は内容によって変わります。

自分のファイルの正確なサイズを知るには、画像→Base64変換ツールやトップページのエンコーダーを使い、元のファイルサイズと比較してください。4/3という比率の仕組みはBase64エンコードとは？その仕組みで、オーバーヘッドの異なる代替手段はBase64・16進・Base32・Base85：どのエンコードを使うべきかでご覧いただけます。
