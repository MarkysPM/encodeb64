Base64URL vs Base64: 차이점과 각각의 사용 시점

2026년 8월읽는 시간 약 4분

JWT 토큰, OAuth 2.0, URL 파라미터를 다뤄본 적이 있다면 Base64URL을 접해봤을 가능성이 높습니다. 이는 표준 Base64의 변형으로 거의 동일해 보이지만 특정 상황에서 다르게 동작합니다. 이 차이를 이해하면 알 수 없는 인코딩 오류를 디버깅하는 데 몇 시간을 아낄 수 있습니다.

표준 Base64란?

RFC 4648 §4에 정의된 표준 Base64는 64개의 문자를 사용해 바이너리 데이터를 인코딩합니다: A–Z, a–z, 0–9, 플러스(+), 슬래시(/). 출력 길이를 4의 배수로 맞추기 위해 등호(=)로 패딩됩니다. 예를 들어 "Man"을 인코딩하면 "TWFu"가 됩니다.

문제는 표준 Base64 문자열을 URL에서 사용하려고 할 때 발생합니다. + 문자는 URL 쿼리 문자열에서 공백으로 해석되고, /는 경로 구분자입니다. "abc+def/ghi="와 같은 Base64 문자열을 URL에 넣으면 웹 서버와 브라우저가 잘못 해석하게 됩니다.

Base64URL이란?

RFC 4648 §5에 정의된 Base64URL은 두 가지 치환으로 이 문제를 해결합니다:

  • +는 -(하이픈)으로 대체
  • /는 _(언더스코어)로 대체
  • = 패딩은 완전히 생략

이 문자들은 퍼센트 인코딩 없이도 URL과 파일명에서 안전합니다. 같은 "Man" 예시는 두 방식 모두 "TWFu"로 인코딩되지만(이 경우 특수문자가 없기 때문), 표준 Base64의 "i+Uo/A=="와 같은 문자열은 Base64URL에서 "i-Uo_A"가 됩니다.

JWT 토큰은 Base64URL을 사용합니다

JSON Web Token(JWT)은 개발자가 Base64URL을 가장 흔하게 접하는 곳입니다. JWT는 점으로 구분된 세 부분으로 구성됩니다: header.payload.signature. 헤더와 페이로드 모두 Base64URL로 인코딩되며, 표준 Base64가 아닙니다. 이것이 JWT 문자열에 하이픈과 언더스코어는 포함되지만 플러스 기호나 슬래시는 절대 포함되지 않는 이유입니다.

문자를 먼저 변환하지 않고 JWT를 표준 Base64 디코더에 붙여넣으면 디코딩 오류나 알아볼 수 없는 결과가 나옵니다. JWT에는 항상 Base64URL을 지원하는 디코더를 사용하세요.

두 방식 간 변환하기

표준 Base64 문자열을 Base64URL로 변환하려면:

  1. 모든 +를 -로 대체
  2. 모든 /를 _로 대체
  3. 모든 = 패딩 문자 제거

Base64URL을 다시 표준 Base64로 변환하려면:

  1. 모든 -를 +로 대체
  2. 모든 _를 /로 대체
  3. 문자열 길이가 4의 배수가 될 때까지 = 패딩 추가

각각의 사용 시점

다음의 경우 표준 Base64를 사용하세요:

  • 이메일 첨부파일 인코딩(MIME, RFC 2045)
  • HTML과 CSS에서 이미지를 Data URI로 삽입
  • 값이 인용부호로 감싸인 JSON 또는 XML 페이로드에 바이너리 데이터 저장
  • 표준 Base64를 구체적으로 요구하는 시스템 작업

다음의 경우 Base64URL을 사용하세요:

  • JWT 토큰 생성 또는 파싱
  • OAuth 2.0 PKCE 챌린지를 위한 URL-safe 토큰 생성
  • URL 쿼리 파라미터나 경로 세그먼트용 데이터 인코딩
  • 바이너리 데이터로 파일명 생성(대부분의 시스템에서 파일명에는 /를 포함할 수 없음)
  • 일반적으로 Base64URL을 출력하는 웹 암호화 API 작업
