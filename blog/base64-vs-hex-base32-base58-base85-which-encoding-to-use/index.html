Base64 vs Hex vs Base32 vs Base85: Which Encoding to Use?

November 20267 min read

When you need to represent binary data as text, Base64 is the default choice, but it is far from the only one. Hexadecimal, Base32, Base58 and Base85 all solve the same problem with different trade-offs in size, readability and safety. Picking the wrong one leads to bloated payloads, case-sensitivity bugs or strings that people cannot type correctly. This guide compares them with real measurements and gives you a simple way to choose.

The Core Idea: Bits per Character

Every text encoding of bytes is defined by one number: how many bits of data each output character carries. A larger alphabet carries more bits per character and produces shorter output.

  • Hex (Base16) has 16 symbols, so each character carries 4 bits.
  • Base32 has 32 symbols, so each character carries 5 bits.
  • Base64 has 64 symbols, so each character carries 6 bits.
  • Base85 has 85 symbols, so on average each character carries a little over 6.4 bits.

The price of a bigger alphabet is that it includes more punctuation and mixed case, which are harder to read aloud, harder to type and more likely to be damaged by systems that change case or treat symbols specially.

Measured Size Overhead

To compare the encodings fairly, I encoded 1,000 random bytes with Python’s standard library and counted the output characters:

  • Hex (Base16): 2,000 characters (+100%)
  • Base32: 1,600 characters (+60%)
  • Base64: 1,336 characters (+33.6%)
  • Base85 / Ascii85: 1,250 characters (+25%)

Base58 is not a power-of-two alphabet, so its length depends on the data, but it lands between Base64 and Base32 in practice, at roughly 37% overhead.

Hex (Base16)

Hex writes every byte as two characters from 0-9 and a-f. It is the least efficient option but also the easiest to read, because one byte always maps to exactly two characters and you can see individual byte values.

Hello → 48656c6c6f

Use it for: hashes and checksums (SHA-256 digests are almost always shown in hex), colors, MAC addresses, debugging dumps and anything a human needs to inspect byte by byte. It is also immune to case and symbol problems in practice, since it uses only digits and letters.

Base32

Base32 uses the letters A-Z and the digits 2-7. It was designed to be safe in case-insensitive systems and to avoid characters that look alike, such as 0 and O or 1 and I.

Hello → JBSWY3DP

Use it for: values people have to type or read aloud, and values stored in case-insensitive places such as some file systems and DNS names. The best-known example is the secret key shown when you set up two-factor authentication with an authenticator app. Output is padded with = to a multiple of eight characters.

Base64

Base64 uses A-Z, a-z, 0-9, + and /. It is the best general-purpose balance between compactness and universal support: every language has it built in, and it is the format expected by email, data URIs, JSON APIs and many protocols.

Hello → SGVsbG8=

Use it for: embedding files in JSON, XML, HTML and CSS, email attachments, cryptographic keys and certificates in PEM files, and most APIs that carry binary data. The URL-safe variant, Base64URL, swaps + and / for - and _; see Base64URL vs Base64.

Base58

Base58 is Base64 with the confusing characters removed: it leaves out 0 (zero), O (capital o), I (capital i), l (lowercase L), and the symbols + and /. The result is a string that is easy to copy by hand and safe to double-click-select in most programs, because it has no punctuation.

Use it for: identifiers that humans transcribe, such as cryptocurrency addresses and some short IDs. Its downside is that, unlike the power-of-two alphabets, encoding and decoding require big-number arithmetic, so it is slower and not suited to large data. It is also not part of most standard libraries, so you usually need a package.

Base85 (Ascii85)

Base85 packs four bytes into five characters, giving the lowest overhead of the text encodings here: 25%. It uses a large alphabet that includes many symbols, which makes it compact but awkward in places where punctuation has special meaning.

Use it for: formats where space matters and the carrier is controlled, such as PDF and PostScript. Git uses a variant to embed binary patches. Python offers base64.a85encode() and base64.b85encode(), but support in other languages is less universal than for Base64.

A Quick Decision Guide

  • Humans will read bytes (hashes, debugging)? Use hex.
  • Humans will type or say the value aloud, or it must survive case-folding? Use Base32 (or Base58 if case is preserved).
  • Machines exchange binary data through text APIs, JSON, HTML or email? Use Base64.
  • The value goes into a URL, filename or JWT? Use Base64URL.
  • Every byte of size counts and you control both ends? Consider Base85, or better, avoid text encoding altogether and send raw bytes.

The Best Encoding Is Sometimes None

Every encoding above adds overhead. If your protocol can carry raw bytes, such as a binary file upload with multipart/form-data, a binary column in a database or gRPC, use that instead. Reach for a text encoding only when the channel forces you to.
