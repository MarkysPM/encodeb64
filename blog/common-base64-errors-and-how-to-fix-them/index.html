Common Base64 Errors and How to Fix Them

November 20268 min read

Base64 is simple, yet it produces some of the most confusing error messages in programming: Incorrect padding, Invalid character, The input is not a valid Base-64 string. The messages differ by language, but the causes are almost always the same handful of problems. This guide lists them in the order you should check them, with the symptom, the cause and the fix for each.

Step One: Look at the String

Before changing code, look at the actual string you are trying to decode. Four quick checks answer most questions:

  • Does it contain - or _? Then it is Base64URL, not standard Base64.
  • Does it contain + or /? Then it is standard Base64.
  • Does it end with = or ==? If it should but does not, the padding was stripped.
  • Does it start with data:? Then it is a data URI and only the part after the comma is Base64.

1. Missing or Wrong Padding

Symptoms: Incorrect padding (Python), illegal base64 data at input byte N (Go), Invalid length for a Base-64 char array (.NET).

Cause: the string’s length is not a multiple of four because the trailing = characters were removed, which is normal in JWTs, URLs and some APIs.

Fix: add the missing padding before decoding. The number of = characters needed is (4 - length % 4) % 4:

def fix_padding(s): return s + '=' * (-len(s) % 4)

A useful sanity check: a valid Base64 string, with or without padding, can never have a length of 1 modulo 4. If length % 4 == 1, the data is truncated or corrupted and no amount of padding will fix it.

2. Standard vs URL-Safe Alphabet Mix-Up

Symptoms: Invalid character or Illegal base64 character 2d (where 2d is the hex code of a hyphen), or output that decodes without an error but is wrong.

Cause: a Base64URL string (with - and _) was fed to a standard decoder, or the reverse.

Fix: use the decoder that matches the data, or translate the characters first: replace - with + and _ with / to go from URL-safe to standard. See Base64URL vs Base64 for when each is used.

3. Plus Signs Turned Into Spaces

Symptoms: the decoded data is corrupted, or the decoder complains about a space character, but only for values that came through a URL or an HTML form.

Cause: in URL query strings and form bodies, a + means a space. A standard Base64 value that was placed in a URL without percent-encoding arrives with its + characters replaced by spaces.

Fix: never put standard Base64 in a URL unescaped. Either percent-encode it (+ becomes %2B, / becomes %2F, = becomes %3D) or, better, use Base64URL. As a rescue on the receiving side, replace spaces with + before decoding.

4. Whitespace and Line Breaks

Symptoms: Illegal base64 character 20 (space) or 0a (line feed) in Java, FormatException in .NET, or a failure only on long values.

Cause: the value was wrapped at 76 characters, copied from an email or a PEM file, or has a trailing newline.

Fix: strip whitespace before decoding (re.sub(r'\s+', '', s) in Python, s.replace(/\s+/g, '') in JavaScript), or use a decoder that tolerates it, such as Java’s MIME decoder. Also watch for the trailing newline added by echo when you encode on the command line.

5. Including the Data URI Prefix

Symptoms: an error mentioning the colon or semicolon, or garbled output when decoding something copied from an <img src> attribute.

Cause: the decoder received data:image/png;base64,iVBORw0... instead of only iVBORw0....

Fix: split on the first comma and decode only the second part: s.split(',', 1)[1]. If you only need the image, you can also use the Base64 string directly as a src after adding the prefix. Our Image to Base64 converter produces both forms.

6. Text Decodes to Garbage or Strange Characters

Symptoms: the decode succeeds but the text contains Ã©, â€™ or question marks.

Cause: a character-encoding mismatch. The bytes are UTF-8, but they were interpreted as Latin-1 or Windows-1252. The reverse also happens: text encoded as UTF-16 (the default for Encoding.Unicode in .NET and -EncodedCommand in PowerShell) decoded as UTF-8 shows null characters between letters.

Fix: make both sides agree on the text encoding, and use UTF-8 unless you have a reason not to. If the decoded data is not text at all (an image, a PDF, an encrypted blob), do not convert it to a string; keep it as bytes.

7. Double Encoding

Symptoms: after decoding, you get another Base64-looking string, often starting with ey or SG.

Cause: the data was encoded twice, usually because one layer of your code and one library both applied Base64.

Fix: decode again and then remove the extra encoding step at the source. A quick test is that real Base64 of ordinary text typically starts with a letter, and a result that is itself valid Base64 is a strong sign of double encoding.

8. Truncated or Corrupted Data

Symptoms: an error at a specific byte position, a length of 1 modulo 4, or a file that opens partially.

Cause: the string was cut by a column limit, a log line limit, a URL length limit or a copy-and-paste mistake.

Fix: compare the length of the string at the source and at the destination, and check the limits of every system in between. Base64 has no error detection, so if you need integrity, send a checksum separately.

9. The Wrong Kind of Input

Symptoms: decoding a hash, a UUID or a hex string and receiving unreadable bytes.

Cause: not every string that looks like Base64 is Base64. Hex strings and some identifiers use only characters that also exist in the Base64 alphabet, so a decoder will happily decode them to meaningless bytes.

Fix: confirm the format with whoever produced the data. Hex uses only 0-9 and a-f and has an even length.

A Debugging Checklist

  1. Print the exact string and its length.
  2. Identify the alphabet (+/ or -_).
  3. Remove whitespace and any data: prefix.
  4. Restore padding if the length is not a multiple of four.
  5. Decode to bytes and only then decide whether it is text.
  6. If it still fails, paste the string into decodeb64.com to confirm whether the problem is the data or your code.
