What Is Base64 Encoding and How Does It Work?

November 20267 min read

Base64 is a way of writing binary data using only 64 printable characters. It is used everywhere you need to move bytes through a channel that only understands text: email attachments, JSON payloads, HTML and CSS data URIs, HTTP headers, JWT tokens and configuration files. Despite how common it is, Base64 is often treated as a black box. This guide explains exactly what it does, one step at a time.

Why Base64 Exists

Many protocols were designed for text, not arbitrary bytes. Early email systems (SMTP) only guaranteed that 7-bit ASCII text would arrive intact. A JPEG, a PDF or an encrypted blob contains byte values that can be mistaken for control characters, line endings or end-of-message markers, and the transport may silently alter or reject them.

Base64 solves this by converting any sequence of bytes into a string made only of letters, digits, + and /. Those characters survive almost every text channel unchanged. The receiver reverses the process and recovers the original bytes exactly.

The Base64 Alphabet

The 64 characters of the standard alphabet (RFC 4648) are:

  • Values 0–25: A to Z
  • Values 26–51: a to z
  • Values 52–61: 0 to 9
  • Value 62: +
  • Value 63: /

A 65th character, =, is used only as padding at the end of the output.

How the Algorithm Works

A byte has 8 bits, but a Base64 character can represent only 6 bits (26 = 64 values). The algorithm therefore regroups the input bits:

  1. Take the input three bytes at a time (24 bits).
  2. Split those 24 bits into four groups of 6 bits.
  3. Look up each 6-bit value in the alphabet to get four output characters.

Three bytes in, four characters out. That ratio is the reason for the size overhead discussed below.

A Worked Example: Encoding “Man”

The text Man is three bytes in ASCII: M = 77, a = 97, n = 110. In binary:

M = 01001101 a = 01100001 n = 01101110

Concatenate the 24 bits and split them into four groups of six:

010011 010110 000101 101110

Those groups are the numbers 19, 22, 5 and 46. Looking them up in the alphabet gives T, W, F and u. So:

Man → TWFu

You can verify this by pasting Man into the encoder on the home page.

Padding With =

Input whose length is not a multiple of three leaves a final group that is short. Base64 handles this by padding the bits with zeros and adding = characters so the output length is always a multiple of four:

  • One leftover byte produces two characters plus ==. Example: M → TQ==
  • Two leftover bytes produce three characters plus =. Example: Ma → TWE=
  • No leftover bytes produce no padding. Example: Man → TWFu

Padding lets a decoder know exactly how many real bytes the last group holds. Some formats, such as Base64URL in JWTs, drop the padding because the length can be inferred.

The 33% Size Overhead

Because every 3 bytes become 4 characters, Base64 output is about 33% larger than the input (4/3 of the original size, rounded up to a multiple of four). A 300 KB image becomes roughly 400 KB of text. If the Base64 is then wrapped across lines, as MIME email does every 76 characters, the overhead grows slightly more. This is the main reason not to Base64-encode large files when a binary-safe channel is available.

Base64 Variants

  • Standard Base64 uses + and / with = padding.
  • Base64URL replaces + with - and / with _ so the result is safe in URLs and file names. See Base64URL vs Base64.
  • MIME Base64 inserts a line break every 76 characters, as required by email.

What Base64 Is Not

Base64 is an encoding, not encryption. Anyone can reverse it instantly, and it provides no confidentiality. Never use it to hide passwords, API keys or personal data. If you need secrecy, encrypt the data first and then, if necessary, Base64-encode the ciphertext for transport.

When to Use Base64

Base64 is a good fit when you must carry binary data inside a text-only format: embedding a small image in HTML or CSS, putting a file inside a JSON API request, storing a binary key in a configuration file, or sending attachments by email. It is a poor fit for large files, for data that your transport can already carry as raw bytes, and for anything that needs to be secret.
