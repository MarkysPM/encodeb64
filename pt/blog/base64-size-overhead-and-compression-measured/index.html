Quanto maior fica o Base64? Tamanho e compressão medidos

Novembro de 20266 min de leitura

O conselho habitual é que o Base64 deixa os dados cerca de 33% maiores. É verdade, mas é só parte da história, porque os servidores web comprimem as respostas e o efeito da compressão sobre o Base64 depende muito do que há dentro. Este artigo traz medições reais, explica os resultados e diz quando a sobrecarga realmente custa algo.

Como as medições foram feitas

Gerei dados de teste com Python 3, codifiquei com o módulo padrão base64 e comprimi com gzip no nível máximo de compressão. Foram usados dois tipos de entrada:

  • Bytes aleatórios, que se comportam como dados já comprimidos ou criptografados: imagens JPEG e PNG, arquivos ZIP, blocos criptografados.
  • Texto real: os 110.508 bytes do código-fonte HTML da página inicial deste site.

Os números abaixo vêm dessa execução de 12 de novembro de 2026. Os tamanhos exatos da compressão podem variar um pouco entre ferramentas e configurações, mas o padrão geral é estável.

Resultado 1: a sobrecarga bruta é 4/3

Para dados aleatórios de tamanhos diferentes, a saída Base64 é:

  • 1.024 bytes viram 1.368 bytes (proporção 1,336)
  • 10.240 bytes viram 13.656 bytes (proporção 1,334)
  • 102.400 bytes viram 136.536 bytes (proporção 1,333)
  • 1.048.576 bytes (1 MB) viram 1.398.104 bytes (proporção 1,333)

A proporção converge exatamente para 4/3, cerca de 33,3%. Entradas pequenas mostram um pouco mais por causa do preenchimento: a saída Base64 é sempre múltiplo de quatro caracteres, então 1, 2 e 3 bytes de entrada produzem 4 caracteres, enquanto 4, 5 e 6 bytes produzem 8.

Resultado 2: o gzip quase anula a sobrecarga em dados aleatórios

O Base64 usa apenas 64 símbolos diferentes, então cada caractere carrega 6 bits de informação em um byte de 8 bits. Um bom compressor enxerga esse espaço desperdiçado e o recupera. Para a amostra de 1 MB:

  • Bytes aleatórios brutos, comprimidos: 1.048.914 bytes (essencialmente sem mudança, como esperado para dados aleatórios)
  • Base64 dos mesmos bytes: 1.398.104 bytes
  • Base64 e depois comprimido: 1.059.032 bytes

Depois do gzip, a versão Base64 fica apenas cerca de 1% maior que o binário original. Ou seja, se o seu servidor comprime a resposta, a penalidade de 33% de imagens e outros arquivos já comprimidos em Base64 some em grande parte durante a transferência. O Brotli se comporta de forma parecida.

Duas ressalvas importam. Primeiro, isso só ajuda se o texto Base64 for realmente comprimido em trânsito; uma API JSON ou página HTML servida sem compressão paga os 33% inteiros. Segundo, o navegador ainda precisa descomprimir e decodificar os dados, o que custa tempo de CPU que uma imagem binária normal não exige.

Resultado 3: o Base64 prejudica a compressão de texto

Dados compressíveis se comportam de outra forma. Para a página HTML de 110.508 bytes:

  • Original: 110.508 bytes
  • Base64: 147.344 bytes (proporção 1,333)
  • Original, com gzip: 27.294 bytes (24,7% do original)
  • Base64, com gzip: 43.007 bytes (38,9% do original)

O Base64 embaralha os padrões que os compressores usam. O gzip ainda consegue reduzir bastante o texto codificado, mas o resultado é cerca de 58% maior do que comprimir diretamente o texto original. Se puder escolher, envie texto como texto.

Resultado 4: a quebra de linhas acrescenta um pouco mais

O Base64 no estilo MIME, usado em e-mail, insere uma quebra de linha a cada 76 caracteres. Para 1.000 bytes aleatórios, a saída Base64 simples foi de 1.336 caracteres e a versão com linhas quebradas de 1.354, cerca de 1,3% a mais. É pouco, mas é um bom motivo para desativar a quebra ao produzir Base64 para JSON, cabeçalhos HTTP ou URIs de dados.

Quando a sobrecarga importa

  • Canais sem compressão: APIs JSON sem gzip, filas de mensagens, logs e bancos de dados que armazenam texto Base64 pagam os 33% inteiros, mais o custo de CPU de codificar e decodificar.
  • Imagens embutidas: uma URI de dados dentro de HTML ou CSS evita uma requisição, mas não pode ser armazenada em cache separadamente. Uma imagem de 100 KB cresce para cerca de 133 KB de texto, baixados de novo sempre que a página muda. Veja URIs de dados Base64: quando embutir imagens.
  • Arquivos grandes: um upload de 100 MB enviado como JSON Base64 tem cerca de 133 MB na rede sem compressão e precisa ser mantido na memória várias vezes durante o processamento.
  • Clientes com pouca memória: celulares e ambientes embarcados sentem a alocação extra mais cedo.

Quando não importa

  • Valores pequenos: tokens, chaves, identificadores curtos e ícones de poucos kilobytes são pequenos demais para a sobrecarga ser notada.
  • Transporte comprimido de dados já comprimidos: como mostrado acima, gzip ou Brotli anulam a maior parte da penalidade.
  • Cargas de uso único: dados codificados uma vez e consumidos uma vez não perdem nenhum cache.

Regras práticas

  1. Prefira enviar binário como binário (uploads multipart, colunas binárias, gRPC) quando o canal permitir.
  2. Se precisar usar Base64 sobre HTTP, ative gzip ou Brotli no servidor para os tipos de conteúdo relevantes.
  3. Não codifique em Base64 texto que poderia ser enviado como texto.
  4. Desative a quebra de linhas, a menos que um padrão exija.
  5. Meça com seus dados reais: as taxas de compressão dependem do conteúdo.

Para obter os tamanhos exatos dos seus próprios arquivos, use o conversor de imagem para Base64 ou o codificador da página inicial e compare com o tamanho original.
