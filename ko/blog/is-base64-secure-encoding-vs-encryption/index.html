Base64는 안전할까? 인코딩과 암호화의 차이

2026년 11월읽는 시간 약 7분

cGFzc3dvcmQxMjM= 같은 Base64 문자열은 뒤섞인 것처럼 보이고, 이런 겉모습 때문에 많은 사람이 이를 보호 수단으로 여깁니다. 하지만 그렇지 않습니다. Base64는 키도 비밀도 없는 가역적 인코딩이며, 누구나 1초 만에 디코딩할 수 있습니다. 이 가이드는 인코딩과 암호화의 차이를 설명하고, Base64가 보안으로 오해되는 곳을 보여 주며, 비밀 정보와 신뢰할 수 없는 입력을 다루는 실용적인 규칙을 제시합니다.

인코딩은 암호화가 아닙니다

두 개념은 서로 다른 문제를 해결합니다.

  • 인코딩은 데이터가 특정 채널을 통과할 수 있도록 표현을 바꿉니다. 방법은 공개되어 있고 키가 없으며 누구나 되돌릴 수 있습니다. Base64, URL 인코딩, 16진수가 인코딩입니다.
  • 암호화는 올바른 키를 가진 사람만 읽을 수 있도록 데이터를 변환합니다. AES처럼 방법이 공개되어 있어도, 키가 없으면 데이터는 읽을 수 없습니다.
  • 해싱은 되돌릴 수 없는 고정 크기의 지문을 만듭니다. 무결성 검사와 비밀번호 저장(적절한 비밀번호 해시 함수 사용)에 쓰입니다.

위의 문자열은 어떤 Base64 디코더로든 password123으로 디코딩됩니다. 변환 과정 어디에도 비밀에 의존하는 부분이 없습니다.

Base64가 보안으로 오해되는 곳

HTTP Basic 인증

Basic 인증은 Authorization: Basic 뒤에 사용자이름:비밀번호의 Base64를 보냅니다. Base64는 특수 문자가 헤더에서 온전히 전달되도록 하려는 용도일 뿐입니다. 요청을 볼 수 있는 사람은 누구나 자격 증명을 읽을 수 있으므로, Basic 인증은 반드시 HTTPS에서만 사용해야 합니다.

JSON Web Token

JWT의 헤더와 페이로드는 암호화된 것이 아니라 Base64URL로 인코딩된 것입니다. 토큰을 가진 사람은 누구나 그 안의 모든 클레임을 읽을 수 있습니다. 서명은 토큰이 변조되지 않았음을 증명할 뿐 내용을 숨기지 않습니다. 표준 서명 JWT에 비밀 정보나 민감한 개인 데이터를 넣지 마세요. 자세한 내용은 JWT 토큰이 Base64URL 인코딩을 사용하는 방식을 참고하세요.

Kubernetes Secret

Kubernetes Secret 매니페스트의 값은 Base64로 인코딩됩니다. 이는 바이너리를 안전하게 저장하기 위한 형식상의 요구사항이지 보호가 아닙니다. 기본적으로 Secret은 클러스터의 데이터 저장소에 암호화되지 않은 채 저장되므로, 이를 보호하는 것은 접근 제어와 선택적인 저장 시 암호화입니다. 매니페스트 파일은 민감한 것으로 취급하고 버전 관리에서 제외하세요.

설정 파일과 환경 변수

비밀번호를 Base64로 바꿔 설정 파일, Docker 환경 변수, 모바일 앱에 저장해도 공격자에게 디코딩 단계 하나를 더해 줄 뿐입니다. 클라이언트 애플리케이션 안에 포함되어 배포되는 것은 모두 추출해서 디코딩할 수 있습니다.

공격자의 난독화

악성 스크립트는 가벼운 점검이나 단순한 문자열 검색이 놓치도록 명령을 Base64 안에 숨기는 일이 많습니다. UTF-16 텍스트의 Base64를 요구하는 PowerShell의 -EncodedCommand 옵션이 잘 알려진 예입니다. 방어하는 쪽에서는 로그와 스크립트에 예상치 못한 Base64가 있으면 더 자세히 살펴볼 가치가 있다는 뜻입니다. 디코딩해서 읽어 보세요.

비밀 정보를 제대로 보호하는 방법

  • 최신 인증 암호화 알고리즘으로 암호화하세요. 충분히 검토된 라이브러리의 AES-GCM이나 ChaCha20-Poly1305 같은 것을 쓰세요. 자체 방식을 만들지 마세요.
  • 키와 데이터를 분리하세요. 코드나 설정이 아니라 비밀 관리자나 키 관리 서비스에서 관리하세요.
  • 비밀번호는 해시하세요. Argon2id, scrypt, bcrypt 같은 전용 알고리즘을 쓰세요. 되돌릴 수 있는 방식으로 인코딩하거나 암호화해서 저장하면 안 됩니다.
  • 어디서나 HTTPS를 사용하세요. 자격 증명과 토큰이 전송 중에 암호화됩니다.
  • 암호화한 뒤에 인코딩하세요. 채널이 텍스트를 요구할 때만 해당합니다. 순서는 먼저 암호화하고, 그다음 암호문을 Base64로 바꾸는 것입니다.

Base64 입력을 다룰 때의 보안 위험

Base64 자체는 아무 보호도 제공하지 않지만, 애플리케이션이 외부에서 Base64를 받을 때는 실제 보안상의 고려 사항이 있습니다.

  • 크기 제한. 작은 요청이 큰 버퍼로 디코딩될 수 있습니다. 메모리 고갈을 막으려면 디코딩 전에 들어오는 Base64의 길이를 제한하세요.
  • 디코딩된 내용을 검증하세요. 주장하는 형식과 상관없이 디코딩된 파일은 무엇이든 될 수 있습니다. 실제 파일 형식을 확인하고, 다른 파일처럼 업로드를 검사하세요.
  • 디코딩된 데이터를 신뢰하지 마세요. 디코딩된 값을 데이터베이스 쿼리, 명령, HTML에 사용한다면 매개변수화된 쿼리, 이스케이프, 출력 인코딩 같은 일반적인 보호를 적용하세요.
  • 데이터 URI를 조심하세요. 사용자가 제공한 데이터 URI를 검증 없이 링크나 프레임에 넣지 말고, Content Security Policy에서 img-src처럼 필요한 곳으로만 제한하세요.
  • 엄격한 디코딩. 문자 집합 밖의 문자가 있는 입력은 무시하지 말고 거부하세요. 그래야 서로 다른 구성 요소가 같은 문자열을 다르게 해석하지 않습니다.

Base64를 써도 괜찮은 경우

이 모든 것이 Base64가 나쁘다는 뜻은 아닙니다. 텍스트 채널로 바이너리 데이터를 옮기는 본래의 일에는 꼭 맞는 도구입니다. 실수는 처음부터 설계되지 않은 일을 시키는 것입니다. 데이터가 비밀이 아니라면 Base64만으로 충분합니다. 비밀이라면 암호화하고, Base64는 암호문을 옮기는 용도로만 쓰세요.
