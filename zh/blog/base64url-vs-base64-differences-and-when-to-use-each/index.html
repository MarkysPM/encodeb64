Base64URL 与 Base64：区别及各自的适用场景

2026年8月阅读时间约 4 分钟

如果你曾接触过 JWT 令牌、OAuth 2.0 或 URL 参数，很可能已经遇到过 Base64URL——它是标准 Base64 的一个变体，看起来几乎一样，但在某些场景下表现却不同。理解这个区别可以帮你节省大量调试诡异编码错误的时间。

什么是标准 Base64？

标准 Base64（定义于 RFC 4648 §4）使用 64 个字符对二进制数据进行编码：A–Z、a–z、0–9，加号（+）和斜杠（/），并使用等号（=）进行填充，使长度为 4 的倍数。例如，将 "Man" 编码后得到 "TWFu"。

问题出现在当你试图把标准 Base64 字符串用在 URL 中时。在 URL 查询字符串中，+ 会被解释为空格，而 / 是路径分隔符。像 "abc+def/ghi=" 这样的 Base64 字符串放在 URL 中，会被 Web 服务器和浏览器错误解析。

什么是 Base64URL？

Base64URL（定义于 RFC 4648 §5）通过两处替换解决了这个问题：

  • + 替换为 -（连字符）
  • / 替换为 _（下划线）
  • 完全省略 = 填充符

这些字符在 URL 和文件名中都是安全的，无需进行百分号编码。同样以 "Man" 为例，两种变体都编码为 "TWFu"（因为这个例子没有特殊字符），但像 "i+Uo/A==" 这样的标准 Base64 字符串，在 Base64URL 中会变成 "i-Uo_A"。

JWT 令牌使用 Base64URL

JSON Web Token（JWT）是开发者最常遇到 Base64URL 的地方。一个 JWT 由三个用点分隔的部分组成：header.payload.signature。header 和 payload 都是用 Base64URL 编码的，而不是标准 Base64。这就是为什么 JWT 字符串中会包含连字符和下划线，但绝不会出现加号或斜杠。

如果你没有先转换字符，直接把 JWT 粘贴到标准 Base64 解码器中，会得到解码错误或乱码输出。解码 JWT 时，务必使用支持 Base64URL 的解码器。

两者之间的转换

将标准 Base64 字符串转换为 Base64URL：

  1. 将所有 + 替换为 -
  2. 将所有 / 替换为 _
  3. 去除所有 = 填充字符

将 Base64URL 转换回标准 Base64：

  1. 将所有 - 替换为 +
  2. 将所有 _ 替换为 /
  3. 补上 = 填充符，直到字符串长度为 4 的倍数

各自的适用场景

在以下情况使用标准 Base64：

  • 编码邮件附件（MIME，RFC 2045）
  • 在 HTML 和 CSS 中以 Data URI 形式嵌入图片
  • 在带引号存储值的 JSON 或 XML 负载中保存二进制数据
  • 对接明确要求使用标准 Base64 的系统

在以下情况使用 Base64URL：

  • 生成或解析 JWT 令牌
  • 为 OAuth 2.0 的 PKCE 挑战创建 URL 安全的令牌
  • 为 URL 查询参数或路径片段编码数据
  • 根据二进制数据生成文件名（大多数系统中文件名不能包含 /）
  • 使用通常输出 Base64URL 的 Web 加密 API

使用正确的变体进行编码

在 encodeb64.com 上，你可以通过高级选项中的“URL-safe encoding (Base64URL)”复选框在标准 Base64 和 Base64URL 之间切换。启用该选项后，工具会自动完成字符替换并去除填充符。要解码任意一种变体，可以使用 decodeb64.com。

Base64 与 Base64URL 之间的差异虽小，却很重要。如果不确定，请查看你要对接系统的规范——JWT 始终意味着 Base64URL，而 MIME 始终意味着带换行的标准 Base64。使用错误的变体是 Web 应用中最常见的编码错误原因之一。
