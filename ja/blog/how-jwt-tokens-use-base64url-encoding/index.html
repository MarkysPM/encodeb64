JWTトークンがBase64URLエンコーディングを使う仕組み

2026年8月読了時間約6分

JSON Web Token（JWT）は、認証・認可・サービス間の情報交換に使われ、現代のWeb開発のあらゆる場所に存在します。JWT文字列を詳しく見たことがあれば、ドットで区切られた3つのセクションから構成されており、ランダムなBase64テキストのように見えることに気づくでしょう。JWTがどのように構成されているか、そしてなぜBase64URLを使うのかを理解しておくと、認証関連の問題をデバッグしやすくなり、トークンをより自信を持って扱えるようになります。

JWTの構造

JWTは次のような形をしています：

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

ドットで区切られた3つの部分は次のとおりです：

  1. Header — トークンの種類と署名アルゴリズムを示す
  2. Payload — トークンにエンコードされたクレーム（データ）を含む
  3. Signature — トークンが改ざんされていないことを検証する

なぜ標準Base64ではなくBase64URLなのか？

JWTは通常、HTTPヘッダー（Authorization: Bearer ...）、URLクエリパラメータ、クッキーの中で送信されます。標準Base64は+と/を使いますが、これらはこうした文脈では問題になります——URLでは+はスペースとして解釈され、/はパス区切り文字です。Base64URLはこれらを-と_に置き換え、=パディングを削除することで、パーセントエンコーディングなしにJWT全体をどんなHTTPコンテキストにも安全に含められるようにします。

Headerをデコードする

上記の例のJWTの最初の部分——eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9——は、Base64URLでエンコードされたheaderです。これをデコードすると次のようになります：

{"alg":"HS256","typ":"JWT"}

これは、トークンがHMAC SHA-256で署名されたJWTであることを示しています。「alg」フィールドは非常に重要で、署名を検証する際に受信側サーバーがどのアルゴリズムを使うべきかを伝えます。

Payloadをデコードする

2番目の部分——eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ——は次のようにデコードされます：

{"sub":"1234567890","name":"John Doe","iat":1516239022}

これらがトークンのクレームです。標準的なクレームには次のものがあります：

  • sub（subject） — 通常はユーザーID
  • iat（issued at） — トークンが作成されたときのUnixタイムスタンプ
  • exp（expiration） — トークンが失効するときのUnixタイムスタンプ
  • iss（issuer） — トークンを作成したサービス

署名はデコードできない（Base64URLデータではないため）

3番目の部分は署名——headerとpayloadをシークレットキーと組み合わせた暗号学的ハッシュです。これは、トークンが信頼できる当事者によって作成され、改ざんされていないことを証明します。署名はJSONではなくバイナリの暗号データであるため、読み取り可能なテキストにデコードすることはできません。検証できるのは、シークレットキーを保持しているサーバーだけです。

重要：デコードは検証ではない

よくある誤解として、誰でもJWTのpayloadをデコードしてクレームを読むことができるという点があります。Base64URLエンコーディングはセキュリティを提供するものではなく、単にJSONをURLセーフな文字列として表現する方法にすぎません。セキュリティを提供しているのは署名の検証です。payloadのクレームを信頼する前に、必ずサーバー側でJWTの署名を検証してください。

デバッグのためにJWTをデコードする方法

開発中にJWTを調べるには：

  1. JWT文字列をコピーする
  2. headerまたはpayloadの部分（最初または2番目のドットより前のテキスト）をdecodeb64.comに貼り付ける
  3. デコードされたJSONにクレームが表示される

JWT全体を貼り付けることもできます——ツールはパースできる最初のセクションをデコードします。本番環境でのデバッグには、署名情報も表示してくれる専用のJWTインスペクターを使用してください。

よくあるJWTエンコーディングのエラー

エラー：JWTをデコードすると「Invalid Base64 input」が表示される
原因：-と_の文字を処理できない標準Base64デコーダーを使用しています。Base64URL対応のデコーダーを使用してください。

エラー：payloadに予期しない文字や意味不明な内容が表示される
原因：JWTのクレームに非UTF-8エンコーディングが使われている、または送信中に文字列が破損した可能性があります。切り詰めや文字の置き換えがないか確認してください。

今すぐJWTのデコードを試す

任意のJWTのpayloadをdecodeb64.comに貼り付けてください——デコーダーはBase64URL形式の入力を自動的に処理し、デコード前に-を+に、_を/に変換します。手動での文字置き換えは不要です。

JWTはそのシンプルさにおいて洗練されています：ドットで区切られた3つのBase64URLエンコードセクションが、改ざん防止のために署名されています。その構造を理解しておくことで、認証フローのデバッグ、開発中のトークンクレームの確認、JWTベースの認証を使うサードパーティAPIとの連携がずっと容易になります。
