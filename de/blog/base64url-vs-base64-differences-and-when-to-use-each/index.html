Base64URL vs Base64: Unterschiede und wann man welche Variante verwendet

August 20264 Min. Lesezeit

Wenn Sie schon einmal mit JWT-Tokens, OAuth 2.0 oder URL-Parametern gearbeitet haben, sind Sie wahrscheinlich schon auf Base64URL gestoßen — eine Variante des Standard-Base64, die fast identisch aussieht, sich aber in bestimmten Kontexten anders verhält. Das Verständnis dieses Unterschieds kann Ihnen Stunden beim Debuggen kryptischer Kodierungsfehler ersparen.

Was ist Standard-Base64?

Standard-Base64, definiert in RFC 4648 §4, kodiert Binärdaten mit 64 Zeichen: A–Z, a–z, 0–9, Plus (+) und Schrägstrich (/). Die Ausgabe wird mit Gleichheitszeichen (=) aufgefüllt, damit die Länge ein Vielfaches von 4 ist. Zum Beispiel ergibt die Kodierung von "Man" "TWFu".

Das Problem entsteht, wenn Sie versuchen, eine Standard-Base64-Zeichenfolge in einer URL zu verwenden. Das Zeichen + wird in URL-Query-Strings als Leerzeichen interpretiert, und / ist ein Pfadtrennzeichen. Eine Base64-Zeichenfolge wie "abc+def/ghi=" in einer URL wird von Webservern und Browsern falsch interpretiert.

Was ist Base64URL?

Base64URL, definiert in RFC 4648 §5, löst dies durch zwei Ersetzungen:

  • + wird durch - (Bindestrich) ersetzt
  • / wird durch _ (Unterstrich) ersetzt
  • das =-Padding wird komplett weggelassen

Alle diese Zeichen sind in URLs und Dateinamen ohne Prozent-Kodierung sicher. Dasselbe Beispiel "Man" wird in beiden Varianten zu "TWFu" kodiert (in diesem Fall keine Sonderzeichen), aber eine Zeichenfolge wie "i+Uo/A==" in Standard-Base64 wird in Base64URL zu "i-Uo_A".

JWT-Tokens verwenden Base64URL

JSON Web Tokens (JWT) sind der häufigste Ort, an dem Entwickler auf Base64URL treffen. Ein JWT besteht aus drei durch Punkte getrennten Teilen: header.payload.signature. Sowohl Header als auch Payload sind Base64URL-kodiert — nicht Standard-Base64. Deshalb enthalten JWT-Strings Bindestriche und Unterstriche, aber niemals Pluszeichen oder Schrägstriche.

Wenn Sie ein JWT in einen Standard-Base64-Decoder einfügen, ohne die Zeichen vorher zu konvertieren, erhalten Sie einen Dekodierungsfehler oder unsinnige Ausgabe. Verwenden Sie für JWTs immer einen Base64URL-fähigen Decoder.

Umwandlung zwischen beiden

So wandeln Sie eine Standard-Base64-Zeichenfolge in Base64URL um:

  1. Ersetzen Sie alle + durch -
  2. Ersetzen Sie alle / durch _
  3. Entfernen Sie alle =-Padding-Zeichen

So wandeln Sie Base64URL zurück in Standard-Base64 um:

  1. Ersetzen Sie alle - durch +
  2. Ersetzen Sie alle _ durch /
  3. Fügen Sie =-Padding hinzu, bis die Länge der Zeichenfolge ein Vielfaches von 4 ist

Wann welche Variante verwenden

Verwenden Sie Standard-Base64, wenn Sie:

  • E-Mail-Anhänge kodieren (MIME, RFC 2045)
  • Bilder als Data URIs in HTML und CSS einbetten
  • Binärdaten in JSON- oder XML-Payloads speichern, bei denen der Wert in Anführungszeichen steht
  • Mit Systemen arbeiten, die speziell Standard-Base64 erfordern

Verwenden Sie Base64URL, wenn Sie:

  • JWT-Tokens erzeugen oder parsen
  • URL-sichere Tokens für OAuth-2.0-PKCE-Challenges erstellen
  • Daten für URL-Query-Parameter oder Pfadsegmente kodieren
  • Dateinamen aus Binärdaten erstellen (Dateinamen dürfen auf den meisten Systemen kein / enthalten)
  • Mit Web-Kryptografie-APIs arbeiten, die typischerweise Base64URL ausgeben

Mit der richtigen Variante kodieren

Auf encodeb64.com können Sie über die Checkbox „URL-safe encoding (Base64URL)" in den erweiterten Optionen zwischen Standard-Base64 und Base64URL wechseln. Das Tool wendet die Zeichenersetzungen automatisch an und entfernt das Padding, wenn diese Option aktiviert ist. Zum Dekodieren beider Varianten nutzen Sie decodeb64.com.

Der Unterschied zwischen Base64 und Base64URL ist klein, aber wichtig. Prüfen Sie im Zweifel die Spezifikation des Systems, mit dem Sie integrieren — JWT bedeutet immer Base64URL, während MIME immer Standard-Base64 mit Zeilenumbrüchen bedeutet. Die Verwendung der falschen Variante ist eine der häufigsten Ursachen für Kodierungsfehler in Webanwendungen.
