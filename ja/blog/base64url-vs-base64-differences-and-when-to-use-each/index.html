Base64URLとBase64の違いと使い分け

2026年8月読了時間約4分

JWTトークン、OAuth 2.0、URLパラメータを扱ったことがあれば、おそらくBase64URLに遭遇したことがあるでしょう。これは標準Base64の変種で、見た目はほぼ同じですが、特定の状況では異なる挙動をします。この違いを理解しておくと、原因不明のエンコードエラーのデバッグに何時間も費やすことを避けられます。

標準Base64とは？

RFC 4648 §4で定義されている標準Base64は、64種類の文字（A–Z、a–z、0–9、プラス記号（+）、スラッシュ（/））を使ってバイナリデータをエンコードします。出力は、長さが4の倍数になるように等号（=）でパディングされます。例えば、"Man"をエンコードすると"TWFu"になります。

問題は、標準Base64の文字列をURLで使おうとしたときに発生します。URLのクエリ文字列では+はスペースとして解釈され、/はパス区切り文字です。"abc+def/ghi="のようなBase64文字列をURLに入れると、Webサーバーやブラウザに誤って解釈されてしまいます。

Base64URLとは？

RFC 4648 §5で定義されているBase64URLは、2つの置き換えによってこの問題を解決します。

  • + を - （ハイフン）に置き換える
  • / を _ （アンダースコア）に置き換える
  • = パディングを完全に省略する

これらの文字は、パーセントエンコーディングなしでURLやファイル名の中でも安全です。同じ"Man"の例では、この場合特殊文字がないためどちらの方式でも"TWFu"になりますが、標準Base64の"i+Uo/A=="のような文字列は、Base64URLでは"i-Uo_A"になります。

JWTトークンはBase64URLを使用する

JSON Web Token（JWT）は、開発者が最もよくBase64URLに遭遇する場面です。JWTはドットで区切られた3つの部分から構成されます：header.payload.signature。ヘッダーとペイロードはいずれもBase64URLでエンコードされており、標準Base64ではありません。そのため、JWTの文字列にはハイフンとアンダースコアが含まれますが、プラス記号やスラッシュは決して含まれません。

文字を変換せずにJWTを標準Base64デコーダーに貼り付けると、デコードエラーや意味不明な出力になります。JWTには常にBase64URLに対応したデコーダーを使用してください。

両者間の変換

標準Base64文字列をBase64URLに変換するには：

  1. すべての + を - に置き換える
  2. すべての / を _ に置き換える
  3. すべての = パディング文字を削除する

Base64URLを標準Base64に戻すには：

  1. すべての - を + に置き換える
  2. すべての _ を / に置き換える
  3. 文字列の長さが4の倍数になるまで = パディングを追加する

それぞれの使い分け

次の場合は標準Base64を使用します：

  • メールの添付ファイルをエンコードする（MIME、RFC 2045）
  • HTMLやCSSで画像をData URIとして埋め込む
  • 値が引用符で囲まれるJSONやXMLのペイロードにバイナリデータを保存する
  • 標準Base64を明確に要求するシステムを扱う

次の場合はBase64URLを使用します：

  • JWTトークンを生成またはパースする
  • OAuth 2.0のPKCEチャレンジ用にURLセーフなトークンを作成する
  • URLのクエリパラメータやパスセグメント用にデータをエンコードする
  • バイナリデータからファイル名を作成する（多くのシステムでファイル名に / を含めることはできません）
  • 通常Base64URLを出力するWeb暗号APIを扱う

Base64とBase64URLの違いはわずかですが重要です。迷ったときは、連携するシステムの仕様を確認してください——JWTは常にBase64URLを意味し、MIMEは常に改行付きの標準Base64を意味します。誤った方式を使うことは、Webアプリケーションにおけるエンコードバグの最も一般的な原因の一つです。
