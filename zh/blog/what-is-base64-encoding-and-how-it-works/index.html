什么是 Base64 编码？它是如何工作的？

2026年11月阅读时间约 7 分钟

Base64 是一种只用 64 个可打印字符来表示二进制数据的方法。凡是需要让字节通过只支持文本的通道传输的场合都会用到它：电子邮件附件、JSON 数据、HTML 和 CSS 中的 data URI、HTTP 标头、JWT 令牌以及配置文件。尽管如此常见，Base64 却常被当作一个“黑盒”。本文将一步一步讲清楚它到底做了什么。

为什么需要 Base64

许多协议是为文本而设计的，而不是为任意字节设计的。早期的电子邮件系统（SMTP）只能保证 7 位 ASCII 文本完好无损地送达。JPEG、PDF 或加密数据块中包含的字节值，可能被误认为控制字符、换行符或消息结束标记，传输过程可能会悄悄修改或拒绝这些数据。

Base64 的解决办法是把任意字节序列转换为仅由字母、数字、+ 和 / 组成的字符串。这些字符几乎可以原样通过任何文本通道。接收方再把过程反过来，就能准确还原原始字节。

Base64 字母表

标准字母表（RFC 4648）的 64 个字符如下：

  • 数值 0–25：A 到 Z
  • 数值 26–51：a 到 z
  • 数值 52–61：0 到 9
  • 数值 62：+
  • 数值 63：/

第 65 个字符 = 仅用作输出末尾的填充。

算法如何工作

一个字节有 8 位，而一个 Base64 字符只能表示 6 位（26 = 64 个值）。因此算法会对输入的比特重新分组：

  1. 每次读取三个字节（24 位）的输入。
  2. 把这 24 位拆成四组，每组 6 位。
  3. 在字母表中查找每个 6 位的值，得到四个输出字符。

输入三个字节，输出四个字符。这个比例正是下文所说体积增加的原因。

示例：编码“Man”

文本 Man 在 ASCII 中是三个字节：M = 77，a = 97，n = 110。用二进制表示：

M = 01001101 a = 01100001 n = 01101110

把这 24 位连起来，再拆成四组，每组六位：

010011 010110 000101 101110

这些分组对应的数字是 19、22、5 和 46。在字母表中查找得到 T、W、F 和 u。因此：

Man → TWFu

你可以把 Man 粘贴到首页的编码器中进行验证。

用 = 填充

如果输入长度不是 3 的倍数，最后一组就不完整。Base64 会用零补足比特，并追加 = 字符，使输出长度始终是 4 的倍数：

  • 剩余一个字节，输出两个字符再加 ==。例如：M → TQ==
  • 剩余两个字节，输出三个字符再加 =。例如：Ma → TWE=
  • 没有剩余字节，则无需填充。例如：Man → TWFu

填充让解码器知道最后一组实际包含多少个字节。有些格式（例如 JWT 中的 Base64URL）会省略填充，因为长度可以推算出来。

33% 的体积增加

由于每 3 个字节变成 4 个字符，Base64 的输出比输入大约大 33%（为原始大小的 4/3，并向上取整到 4 的倍数）。一张 300 KB 的图片会变成约 400 KB 的文本。如果输出再被分行（MIME 邮件每 76 个字符换行一次），额外开销还会略有增加。这是在有二进制安全通道可用时，不要用 Base64 编码大文件的主要原因。

Base64 的变体

  • 标准 Base64 使用 + 和 /，并以 = 填充。
  • Base64URL 把 + 换成 -，把 / 换成 _，使结果可安全用于 URL 和文件名。参见 Base64URL 与 Base64。
  • MIME Base64 每 76 个字符插入一个换行，这是电子邮件的要求。

Base64 不是什么

Base64 是一种编码，不是加密。任何人都可以立即还原它，它不提供任何保密性。切勿用它来隐藏密码、API 密钥或个人数据。如果需要保密，请先加密数据，必要时再把密文用 Base64 编码以便传输。

何时使用 Base64

当你必须在纯文本格式中携带二进制数据时，Base64 很合适：在 HTML 或 CSS 中内嵌小图片、把文件放进发给 API 的 JSON 请求、在配置文件中存放二进制密钥，或通过电子邮件发送附件。它不适合大文件，不适合传输方式本来就能直接传递原始字节的数据，也不适合任何需要保密的内容。
