Base64URL vs Base64 : différences et quand utiliser chacun

Août 20264 min de lecture

Si vous avez déjà travaillé avec des jetons JWT, OAuth 2.0 ou des paramètres d'URL, vous avez probablement rencontré Base64URL — une variante du Base64 standard qui semble presque identique mais se comporte différemment dans certains contextes. Comprendre cette distinction peut vous faire gagner des heures de débogage d'erreurs d'encodage cryptiques.

Qu'est-ce que le Base64 standard ?

Le Base64 standard, défini dans la RFC 4648 §4, encode les données binaires en utilisant 64 caractères : A–Z, a–z, 0–9, plus (+) et barre oblique (/). La sortie est complétée par des signes égal (=) pour que la longueur soit un multiple de 4. Par exemple, encoder « Man » donne « TWFu ».

Le problème survient lorsque vous essayez d'utiliser une chaîne Base64 standard dans une URL. Le caractère + est interprété comme un espace dans les chaînes de requête d'URL, et / est un séparateur de chemin. Une chaîne Base64 comme « abc+def/ghi= » placée dans une URL sera mal interprétée par les serveurs web et les navigateurs.

Qu'est-ce que Base64URL ?

Base64URL, défini dans la RFC 4648 §5, résout ce problème en effectuant deux substitutions :

  • + est remplacé par - (tiret)
  • / est remplacé par _ (underscore)
  • le padding = est totalement omis

Ces caractères sont tous sûrs dans les URL et les noms de fichiers sans encodage en pourcentage. Le même exemple « Man » s'encode en « TWFu » dans les deux variantes (aucun caractère spécial dans ce cas), mais une chaîne comme « i+Uo/A== » en Base64 standard devient « i-Uo_A » en Base64URL.

Les jetons JWT utilisent Base64URL

Les JSON Web Tokens (JWT) sont l'endroit le plus courant où les développeurs rencontrent Base64URL. Un JWT se compose de trois parties séparées par des points : header.payload.signature. Le header et le payload sont tous deux encodés en Base64URL — pas en Base64 standard. C'est pourquoi les chaînes JWT contiennent des tirets et des underscores, mais jamais de signes plus ni de barres obliques.

Si vous collez un JWT dans un décodeur Base64 standard sans convertir les caractères au préalable, vous obtiendrez une erreur de décodage ou un résultat illisible. Utilisez toujours un décodeur compatible Base64URL pour les JWT.

Convertir entre les deux

Pour convertir une chaîne Base64 standard en Base64URL :

  1. Remplacez tous les + par -
  2. Remplacez tous les / par _
  3. Supprimez tous les caractères de padding =

Pour reconvertir Base64URL en Base64 standard :

  1. Remplacez tous les - par +
  2. Remplacez tous les _ par /
  3. Ajoutez du padding = jusqu'à ce que la longueur de la chaîne soit un multiple de 4

Quand utiliser chacun

Utilisez Base64 standard pour :

  • Encoder les pièces jointes d'e-mails (MIME, RFC 2045)
  • Intégrer des images en tant que Data URI dans HTML et CSS
  • Stocker des données binaires dans des payloads JSON ou XML où la valeur est entre guillemets
  • Travailler avec des systèmes exigeant spécifiquement le Base64 standard

Utilisez Base64URL pour :

  • Générer ou analyser des jetons JWT
  • Créer des jetons compatibles URL pour les challenges PKCE d'OAuth 2.0
  • Encoder des données pour des paramètres de requête d'URL ou des segments de chemin
  • Créer des noms de fichiers à partir de données binaires (les noms de fichiers ne peuvent pas contenir / sur la plupart des systèmes)
  • Travailler avec des API de cryptographie web, qui produisent généralement du Base64URL

Encoder avec la bonne variante

Sur encodeb64.com, vous pouvez basculer entre Base64 standard et Base64URL grâce à la case « URL-safe encoding (Base64URL) » dans les options avancées. L'outil applique automatiquement les substitutions de caractères et supprime le padding lorsque cette option est activée. Pour décoder l'une ou l'autre variante, utilisez decodeb64.com.

La différence entre Base64 et Base64URL est minime mais importante. En cas de doute, vérifiez la spécification du système avec lequel vous intégrez — JWT signifie toujours Base64URL, tandis que MIME signifie toujours Base64 standard avec retours à la ligne. Utiliser la mauvaise variante est l'une des causes les plus fréquentes de bugs d'encodage dans les applications web.
