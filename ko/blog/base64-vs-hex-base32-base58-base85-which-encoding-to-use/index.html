Base64 vs 16진수 vs Base32 vs Base85: 무엇을 쓸까?

2026년 11월읽는 시간 약 7분

바이너리 데이터를 텍스트로 표현해야 할 때 Base64가 기본 선택이지만, 유일한 선택지는 아닙니다. 16진수, Base32, Base58, Base85도 같은 문제를 해결하며, 크기, 가독성, 견고성에서 서로 다른 절충을 가집니다. 잘못 고르면 페이로드가 부풀거나, 대소문자 관련 버그가 생기거나, 사람이 정확히 입력할 수 없는 문자열이 됩니다. 이 가이드는 실제 측정값으로 이들을 비교하고, 고르는 간단한 기준을 제시합니다.

핵심 개념: 문자당 비트 수

바이트를 텍스트로 바꾸는 모든 인코딩은 하나의 숫자로 정의됩니다. 출력 문자 하나가 몇 비트의 데이터를 담느냐입니다. 문자 집합이 클수록 문자당 비트가 많아지고 출력은 짧아집니다.

  • 16진수(Base16)는 기호가 16개이므로 문자 하나가 4비트를 담습니다.
  • Base32는 기호가 32개이므로 문자 하나가 5비트를 담습니다.
  • Base64는 기호가 64개이므로 문자 하나가 6비트를 담습니다.
  • Base85는 기호가 85개이므로 평균적으로 문자 하나가 6.4비트를 약간 넘게 담습니다.

더 큰 문자 집합의 대가는 구두점과 대소문자 혼용이 늘어난다는 점입니다. 소리 내어 읽거나 입력하기 어려워지고, 대소문자를 바꾸거나 기호를 특별하게 처리하는 시스템에서 손상될 가능성도 커집니다.

실측한 크기 증가

공정하게 비교하기 위해 무작위 바이트 1,000개를 Python 표준 라이브러리로 인코딩하고 출력 문자 수를 셌습니다.

  • 16진수(Base16): 2,000자 (+100%)
  • Base32: 1,600자 (+60%)
  • Base64: 1,336자 (+33.6%)
  • Base85 / Ascii85: 1,250자 (+25%)

Base58은 2의 거듭제곱 문자 집합이 아니라서 길이가 데이터에 따라 달라지지만, 실제로는 Base64와 Base32 사이에 위치하며 약 37%의 오버헤드가 생깁니다.

16진수(Base16)

16진수는 각 바이트를 0-9와 a-f로 이루어진 두 글자로 씁니다. 효율은 가장 낮지만 가장 읽기 쉽습니다. 바이트 하나가 항상 정확히 두 글자에 대응하고 각 바이트 값을 바로 볼 수 있기 때문입니다.

Hello → 48656c6c6f

적합한 용도: 해시와 체크섬(SHA-256 다이제스트는 거의 항상 16진수로 표시됩니다), 색상, MAC 주소, 디버깅 덤프, 사람이 바이트 단위로 살펴봐야 하는 모든 것. 숫자와 글자만 쓰므로 실제로 대소문자나 기호 문제도 거의 없습니다.

Base32

Base32는 알파벳 A-Z와 숫자 2-7을 사용합니다. 대소문자를 구분하지 않는 시스템에서도 안전하고, 0과 O, 1과 I처럼 헷갈리는 문자를 피하도록 설계되었습니다.

Hello → JBSWY3DP

적합한 용도: 사람이 입력하거나 소리 내어 읽어야 하는 값, 일부 파일 시스템이나 DNS 이름처럼 대소문자를 구분하지 않는 곳에 저장되는 값. 가장 잘 알려진 예는 인증 앱으로 2단계 인증을 설정할 때 표시되는 비밀 키입니다. 출력은 8자의 배수가 되도록 =로 채워집니다.

Base64

Base64는 A-Z, a-z, 0-9, +, /를 사용합니다. 간결함과 보편적 지원 사이에서 가장 균형 잡힌 범용 선택입니다. 모든 언어에 내장되어 있고, 이메일, 데이터 URI, JSON API, 많은 프로토콜이 기대하는 형식이기도 합니다.

Hello → SGVsbG8=

적합한 용도: JSON, XML, HTML, CSS에 파일 포함, 이메일 첨부 파일, PEM 파일의 암호 키와 인증서, 바이너리 데이터를 전달하는 대부분의 API. URL 안전 변형인 Base64URL은 +와 /를 -와 _로 바꿉니다. Base64URL과 Base64의 차이를 참고하세요.

Base58

Base58은 헷갈리는 문자를 뺀 Base64입니다. 0(숫자 영), O(대문자 오), I(대문자 아이), l(소문자 엘), 그리고 기호 +와 /를 제외합니다. 그 결과 손으로 옮겨 적기 쉽고, 구두점이 없어서 대부분의 프로그램에서 더블 클릭으로 선택할 수 있는 문자열이 됩니다.

적합한 용도: 암호화폐 주소나 일부 짧은 ID처럼 사람이 옮겨 적는 식별자. 단점은 2의 거듭제곱 문자 집합과 달리 인코딩과 디코딩에 큰 수 연산이 필요해 느리고, 큰 데이터에는 적합하지 않다는 것입니다. 또한 대부분의 표준 라이브러리에 포함되어 있지 않아 보통 별도 패키지가 필요합니다.

Base85(Ascii85)

Base85는 4바이트를 5문자로 묶어, 여기서 다루는 텍스트 인코딩 중 가장 낮은 25%의 오버헤드를 보입니다. 많은 기호를 포함한 큰 문자 집합을 사용하므로 간결하지만, 구두점이 특별한 의미를 갖는 곳에서는 불편합니다.

적합한 용도: PDF나 PostScript처럼 공간이 중요하고 전송 경로를 통제할 수 있는 형식. Git은 바이너리 패치를 포함하기 위해 변형을 사용합니다. Python에는 base64.a85encode()와 base64.b85encode()가 있지만, 다른 언어에서의 지원은 Base64만큼 보편적이지 않습니다.

빠른 선택 가이드

  • 사람이 바이트를 읽는다(해시, 디버깅)? 16진수를 쓰세요.
  • 사람이 값을 입력하거나 말로 전달하거나, 대소문자 변환을 견뎌야 한다? Base32를 쓰세요(대소문자가 유지된다면 Base58도 가능).
  • 기계끼리 텍스트 API, JSON, HTML, 이메일로 바이너리 데이터를 주고받는다? Base64를 쓰세요.
  • 값이 URL, 파일 이름, JWT에 들어간다? Base64URL을 쓰세요.
  • 1바이트가 아쉽고 양쪽 끝을 모두 통제할 수 있다? Base85를 고려하거나, 더 좋게는 텍스트 인코딩 자체를 피하고 원시 바이트를 보내세요.

가장 좋은 인코딩은 때로 인코딩하지 않는 것

위의 모든 인코딩은 오버헤드를 더합니다. 프로토콜이 multipart/form-data를 이용한 바이너리 업로드, 데이터베이스의 바이너리 열, gRPC처럼 원시 바이트를 실을 수 있다면 그것을 쓰세요. 전송 경로가 강제할 때만 텍스트 인코딩을 사용하세요.
