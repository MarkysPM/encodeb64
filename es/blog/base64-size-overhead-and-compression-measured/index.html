¿Cuánto más grande es Base64? Tamaño y compresión medidos

Noviembre de 20266 min de lectura

El consejo habitual es que Base64 hace los datos alrededor de un 33 % más grandes. Es cierto, pero es solo parte de la historia, porque los servidores web comprimen las respuestas y el efecto de la compresión sobre Base64 depende mucho de lo que haya dentro. Este artículo presenta mediciones reales, explica los resultados y te dice cuándo la sobrecarga te cuesta algo de verdad.

Cómo se hicieron las mediciones

Generé datos de prueba con Python 3, los codifiqué con el módulo estándar base64 y los comprimí con gzip al nivel máximo de compresión. Se usaron dos tipos de entrada:

  • Bytes aleatorios, que se comportan como datos ya comprimidos o cifrados: imágenes JPEG y PNG, archivos ZIP, bloques cifrados.
  • Texto real: los 110 508 bytes del código HTML de la página de inicio de este sitio.

Las cifras de abajo salen de esa ejecución del 12 de noviembre de 2026. Los tamaños exactos de la compresión pueden variar algo entre herramientas y ajustes, pero el patrón general es estable.

Resultado 1: la sobrecarga bruta es 4/3

Con datos aleatorios de distintos tamaños, la salida Base64 es:

  • 1024 bytes pasan a 1368 bytes (proporción 1,336)
  • 10 240 bytes pasan a 13 656 bytes (proporción 1,334)
  • 102 400 bytes pasan a 136 536 bytes (proporción 1,333)
  • 1 048 576 bytes (1 MB) pasan a 1 398 104 bytes (proporción 1,333)

La proporción converge exactamente a 4/3, es decir, alrededor del 33,3 %. Las entradas pequeñas muestran algo más por el relleno: la salida Base64 es siempre múltiplo de cuatro caracteres, así que 1, 2 y 3 bytes de entrada producen 4 caracteres, mientras que 4, 5 y 6 bytes producen 8.

Resultado 2: gzip casi anula la sobrecarga con datos aleatorios

Base64 solo usa 64 símbolos distintos, así que cada carácter lleva 6 bits de información en un byte de 8 bits. Un buen compresor ve ese espacio desperdiciado y lo recupera. Con la muestra de 1 MB:

  • Bytes aleatorios crudos, comprimidos: 1 048 914 bytes (esencialmente sin cambio, como se espera de datos aleatorios)
  • Base64 de los mismos bytes: 1 398 104 bytes
  • Base64, y luego comprimido: 1 059 032 bytes

Tras gzip, la versión Base64 es solo un 1 % mayor que el binario original. Es decir, si tu servidor comprime la respuesta, la penalización del 33 % de las imágenes y otros archivos ya comprimidos en Base64 desaparece en gran parte durante la transferencia. Brotli se comporta de forma parecida.

Dos salvedades importan. Primero, esto solo ayuda si el texto Base64 se comprime realmente en tránsito; una API JSON o una página HTML servida sin compresión paga el 33 % completo. Segundo, el navegador tiene que descomprimir y decodificar los datos, lo que cuesta tiempo de CPU que una imagen binaria normal no requiere.

Resultado 3: Base64 perjudica la compresión del texto

Los datos comprimibles se comportan de otra manera. Con la página HTML de 110 508 bytes:

  • Original: 110 508 bytes
  • Base64: 147 344 bytes (proporción 1,333)
  • Original, con gzip: 27 294 bytes (24,7 % del original)
  • Base64, con gzip: 43 007 bytes (38,9 % del original)

Base64 desordena los patrones que usan los compresores. Gzip aún puede reducir mucho el texto codificado, pero el resultado es un 58 % mayor que comprimir directamente el texto original. Si puedes elegir, envía el texto como texto.

Resultado 4: partir las líneas añade un poco más

El Base64 estilo MIME, usado en el correo, inserta un salto de línea cada 76 caracteres. Con 1000 bytes aleatorios, la salida Base64 normal fue de 1336 caracteres y la versión con líneas partidas de 1354, es decir, un 1,3 % más. Es poco, pero es un buen motivo para desactivar el partido de líneas al producir Base64 para JSON, cabeceras HTTP o URI de datos.

Cuándo importa la sobrecarga

  • Canales sin comprimir: las API JSON sin gzip, las colas de mensajes, los registros y las bases de datos que guardan texto Base64 pagan el 33 % completo, más el coste de CPU de codificar y decodificar.
  • Imágenes en línea: una URI de datos dentro de HTML o CSS evita una petición, pero no se puede cachear por separado. Una imagen de 100 KB crece hasta unos 133 KB de texto, que se descargan de nuevo cada vez que cambia la página. Consulta URI de datos Base64: cuándo incrustar imágenes.
  • Archivos grandes: una subida de 100 MB enviada como JSON Base64 son unos 133 MB en la red sin compresión y debe mantenerse en memoria varias veces durante el procesamiento.
  • Clientes con poca memoria: los móviles y los entornos embebidos notan antes la asignación extra.

Cuándo no importa

  • Valores pequeños: tokens, claves, identificadores cortos e iconos de unos pocos kilobytes son demasiado pequeños para que se note la sobrecarga.
  • Transporte comprimido de datos ya comprimidos: como se vio arriba, gzip o Brotli anulan la mayor parte de la penalización.
  • Cargas de un solo uso: los datos que se codifican una vez y se consumen una vez no pierden ninguna caché.

Reglas prácticas

  1. Prefiere enviar binario como binario (subidas multipart, columnas binarias, gRPC) cuando el canal lo permita.
  2. Si debes usar Base64 sobre HTTP, activa gzip o Brotli en el servidor para los tipos de contenido relevantes.
  3. No codifiques en Base64 texto que podrías enviar como texto.
  4. Desactiva el partido de líneas salvo que lo exija un estándar.
  5. Mide con tus datos reales: las proporciones de compresión dependen del contenido.

Para obtener los tamaños exactos de tus propios archivos, usa el conversor de imagen a Base64 o el codificador de la página de inicio y compáralos con el tamaño original. Para la mecánica de la proporción 4/3, lee ¿Qué es Base64 y cómo funciona la codificación? y, para alternativas con otra sobrecarga, consulta Base64 vs Hex vs Base32 vs Base85.
