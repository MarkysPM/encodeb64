Base64 on the Command Line: Linux, macOS and Windows

November 20266 min read

You do not need a website or a script to work with Base64. Every major operating system ships with tools that can encode and decode it from the terminal, which is handy for inspecting tokens, creating secrets for configuration files or converting small files. This guide covers Linux, macOS and Windows, and points out the differences that cause confusing results.

Linux: the base64 Command

The GNU base64 command is part of coreutils and is installed on virtually every Linux distribution.

Encode a string:

echo -n 'Hello, World!' | base64 # SGVsbG8sIFdvcmxkIQ==

Decode it:

echo 'SGVsbG8sIFdvcmxkIQ==' | base64 --decode # Hello, World!

Encode and decode files:

base64 photo.png > photo.b64 base64 --decode photo.b64 > photo-copy.png

The Trailing Newline Trap

This is the most common mistake. Plain echo adds a newline character to its output, and that newline becomes part of the data being encoded:

echo 'Hello' | base64 # SGVsbG8K (encodes "Hello\n") echo -n 'Hello' | base64 # SGVsbG8= (encodes "Hello")

If a password, API key or token “does not work” after you encoded it in the terminal, an extra newline is the likely culprit. Always use echo -n, or use printf '%s' 'Hello', which behaves the same on every shell.

Line Wrapping

GNU base64 wraps its output after 76 characters. That is fine for files, but not for pasting into JSON, environment variables or HTTP headers. Disable wrapping with -w 0:

base64 -w 0 photo.png

macOS

macOS includes a BSD version of base64 that accepts slightly different options. Basic encoding with a pipe works the same way:

echo -n 'Hello, World!' | base64 echo 'SGVsbG8sIFdvcmxkIQ==' | base64 --decode

Use -i for an input file and -o for an output file:

base64 -i photo.png -o photo.b64

The GNU option -w 0 is not available on macOS, and older macOS versions used -D instead of -d or --decode. If a script has to run on both systems, either test for the platform or use openssl below.

openssl: The Portable Option

OpenSSL is available on Linux, macOS and Windows (through Git for Windows or WSL), and behaves consistently:

echo -n 'Hello, World!' | openssl base64 echo 'SGVsbG8sIFdvcmxkIQ==' | openssl base64 -d openssl base64 -in photo.png -out photo.b64

Add -A to keep the output on a single line instead of wrapping it.

Windows PowerShell

PowerShell can call the .NET Convert class directly. Encode text:

[Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes('Hello, World!')) # SGVsbG8sIFdvcmxkIQ==

Decode text:

[Text.Encoding]::UTF8.GetString([Convert]::FromBase64String('SGVsbG8sIFdvcmxkIQ==')) # Hello, World!

Encode a file to a Base64 string:

[Convert]::ToBase64String([IO.File]::ReadAllBytes('photo.png'))

Decode a Base64 string back into a file:

[IO.File]::WriteAllBytes('photo-copy.png', [Convert]::FromBase64String($base64))

Notice that you choose the text encoding explicitly (UTF8). If you use Unicode instead, PowerShell uses UTF-16, and the result will differ from what Linux and macOS produce.

Windows certutil

The legacy certutil tool works from Command Prompt on any Windows system:

certutil -encode photo.png photo.b64 certutil -decode photo.b64 photo-copy.png

Be aware that certutil -encode wraps the output in -----BEGIN CERTIFICATE----- header and footer lines. Remove those lines if you need only the Base64 text.

Decoding Base64URL From the Terminal

JWTs and many modern APIs use the URL-safe alphabet and drop the padding, so a plain base64 --decode may fail. Convert the characters and restore the padding first:

value='eyJhbGciOiJIUzI1NiJ9' len=$(( ${#value} % 4 )) [ $len -eq 2 ] && value="$value==" [ $len -eq 3 ] && value="$value=" echo "$value" | tr '_-' '/+' | base64 --decode # {"alg":"HS256"}

To understand why these tokens look different, read How JWT Tokens Use Base64URL Encoding.

Quick Comparison

  • Linux: base64, with -w 0 for a single line.
  • macOS: base64 with -i and -o; no -w option.
  • Cross-platform: openssl base64.
  • Windows: PowerShell [Convert] or certutil.
