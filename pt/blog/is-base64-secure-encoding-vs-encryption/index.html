Base64 é seguro? Codificação versus criptografia

Novembro de 20267 min de leitura

Uma string Base64 como cGFzc3dvcmQxMjM= parece embaralhada, e essa aparência leva muita gente a tratá-la como proteção. Não é. Base64 é uma codificação reversível, sem chave nem segredo, e qualquer pessoa a decodifica em um segundo. Este guia explica a diferença entre codificação e criptografia, mostra onde o Base64 é confundido com segurança e dá regras práticas para tratar segredos e entradas não confiáveis.

Codificar não é criptografar

As duas ideias resolvem problemas diferentes:

  • Codificação muda a representação dos dados para que possam trafegar por um canal específico. O método é público, não há chave e qualquer um pode revertê-la. Base64, codificação de URL e hex são codificações.
  • Criptografia transforma os dados para que só quem tem a chave correta possa lê-los. Mesmo que o método seja público, como o AES, os dados continuam ilegíveis sem a chave.
  • Hash produz uma impressão digital de tamanho fixo que não pode ser revertida. É usado para verificar integridade e para guardar senhas (com uma função de hash de senhas adequada).

A string acima decodifica para password123 em qualquer decodificador Base64. Nada na transformação depende de um segredo.

Onde o Base64 é confundido com segurança

Autenticação HTTP Basic

A autenticação Basic envia Authorization: Basic seguido do Base64 de usuário:senha. O Base64 só está ali para que caracteres especiais sobrevivam em um cabeçalho. Quem puder ver a requisição lê as credenciais, por isso a autenticação Basic só deve ser usada sobre HTTPS.

JSON Web Tokens

O cabeçalho e o payload de um JWT são codificados em Base64URL, não criptografados. Quem tiver o token pode ler todas as claims. A assinatura só prova que o token não foi modificado; ela não esconde o conteúdo. Não coloque segredos nem dados pessoais sensíveis em um JWT assinado padrão. Leia mais em Como os tokens JWT usam a codificação Base64URL.

Secrets do Kubernetes

Os valores em um manifesto Secret do Kubernetes são codificados em Base64. É uma exigência de formato para armazenar dados binários, não uma proteção. Por padrão, os Secrets ficam sem criptografia no armazenamento de dados do cluster, então o que os protege é o controle de acesso e a criptografia opcional em repouso. Trate o arquivo de manifesto como sensível e mantenha-o fora do controle de versão.

Arquivos de configuração e variáveis de ambiente

Guardar uma senha como Base64 em um arquivo de configuração, em uma variável de ambiente do Docker ou em um app móvel só acrescenta uma etapa de decodificação para um atacante. Tudo que é distribuído dentro de um aplicativo cliente pode ser extraído e decodificado.

Ofuscação por atacantes

Scripts maliciosos costumam esconder comandos dentro de Base64 para que uma inspeção casual ou uma busca simples de texto não os encontre. A opção -EncodedCommand do PowerShell, que espera Base64 de texto UTF-16, é um exemplo conhecido. Para quem defende, isso significa que Base64 inesperado em logs e scripts merece um olhar mais atento: decodifique e leia.

Como proteger segredos corretamente

  • Use criptografia com um algoritmo autenticado moderno, como AES-GCM ou ChaCha20-Poly1305, de uma biblioteca bem revisada. Não invente seu próprio esquema.
  • Mantenha as chaves separadas dos dados e gerencie-as em um gerenciador de segredos ou serviço de gerenciamento de chaves, não no código nem na configuração.
  • Aplique hash às senhas com um algoritmo próprio, como Argon2id, scrypt ou bcrypt. Nunca as guarde codificadas ou criptografadas de forma reversível.
  • Use HTTPS em todo lugar para que credenciais e tokens sejam criptografados em trânsito.
  • Codifique depois de criptografar, e só se o canal precisar de texto. A ordem é criptografar primeiro e depois converter o texto cifrado para Base64.

Riscos de segurança ao tratar entrada Base64

Embora o Base64 em si não ofereça proteção, há considerações reais de segurança quando sua aplicação aceita Base64 de fora:

  • Limites de tamanho. Uma requisição pequena pode decodificar para um buffer grande. Limite o tamanho do Base64 recebido antes de decodificar para evitar esgotamento de memória.
  • Valide o conteúdo decodificado. Um arquivo decodificado pode ser qualquer coisa, independentemente do tipo declarado. Verifique o tipo real do arquivo e analise os uploads como qualquer outro arquivo.
  • Não confie nos dados decodificados. Se um valor decodificado for usado em uma consulta de banco de dados, um comando ou HTML, aplique as proteções normais: consultas parametrizadas, escape e codificação de saída.
  • Cuidado com URIs de dados. Nunca insira URIs de dados fornecidas pelo usuário em links ou frames sem validar e restrinja-as na sua Content Security Policy aos lugares em que precisa, como img-src.
  • Decodificação estrita. Rejeite entradas com caracteres fora do alfabeto em vez de ignorá-los, para que componentes diferentes não interpretem a mesma string de formas diferentes.

Quando o Base64 é adequado

Nada disso significa que o Base64 seja ruim. É exatamente a ferramenta certa para o seu trabalho: transportar dados binários por canais de texto. O erro é pedir a ele uma tarefa para a qual nunca foi projetado. Se os dados não são secretos, o Base64 sozinho basta. Se são secretos, criptografe-os e use o Base64 apenas para transportar o texto cifrado.
