¿Es seguro Base64? Codificación frente a cifrado

Noviembre de 20267 min de lectura

Una cadena Base64 como cGFzc3dvcmQxMjM= parece revuelta, y esa apariencia lleva a muchas personas a tratarla como una protección. No lo es. Base64 es una codificación reversible sin clave ni secreto, y cualquiera puede decodificarla en un segundo. Esta guía explica la diferencia entre codificación y cifrado, muestra dónde se confunde Base64 con seguridad y da reglas prácticas para manejar secretos y entradas no confiables.

Codificar no es cifrar

Las dos ideas resuelven problemas distintos:

  • La codificación cambia la representación de los datos para que puedan viajar por un canal concreto. El método es público, no hay clave y cualquiera puede revertirla. Base64, la codificación URL y hex son codificaciones.
  • El cifrado transforma los datos para que solo pueda leerlos quien tenga la clave correcta. Aunque el método sea público, como AES, los datos siguen siendo ilegibles sin la clave.
  • El hash produce una huella de tamaño fijo que no se puede revertir. Se usa para comprobar la integridad y para guardar contraseñas (con una función de hash de contraseñas adecuada).

La cadena anterior se decodifica como password123 con cualquier decodificador Base64. Nada de la transformación depende de un secreto.

Dónde se confunde Base64 con seguridad

Autenticación HTTP Basic

La autenticación Basic envía Authorization: Basic seguido del Base64 de usuario:contraseña. El Base64 solo está ahí para que los caracteres especiales sobrevivan en una cabecera. Cualquiera que pueda ver la petición puede leer las credenciales, por lo que la autenticación Basic solo debe usarse sobre HTTPS.

JSON Web Tokens

La cabecera y la carga útil de un JWT están codificadas en Base64URL, no cifradas. Cualquiera que tenga el token puede leer todas sus claims. La firma solo demuestra que el token no se modificó; no oculta el contenido. No pongas secretos ni datos personales sensibles en un JWT firmado estándar. Más información en Cómo usan los tokens JWT la codificación Base64URL.

Secrets de Kubernetes

Los valores de un manifiesto Secret de Kubernetes están codificados en Base64. Es un requisito de formato para guardar datos binarios, no una protección. Por defecto, los Secrets se almacenan sin cifrar en el almacén de datos del clúster, así que lo que los protege es el control de acceso y el cifrado opcional en reposo. Trata el archivo de manifiesto como sensible y mantenlo fuera del control de versiones.

Archivos de configuración y variables de entorno

Guardar una contraseña como Base64 en un archivo de configuración, una variable de entorno de Docker o una app móvil solo añade un paso de decodificación para un atacante. Todo lo que se distribuye dentro de una aplicación cliente puede extraerse y decodificarse.

Ofuscación por parte de atacantes

Los scripts maliciosos suelen esconder comandos dentro de Base64 para que la inspección casual o la búsqueda simple de cadenas no los detecte. La opción -EncodedCommand de PowerShell, que espera Base64 de texto UTF-16, es un ejemplo muy conocido. Para quienes defienden, esto significa que el Base64 inesperado en registros y scripts merece una mirada más atenta: decodifícalo y léelo.

Cómo proteger bien los secretos

  • Usa cifrado con un algoritmo autenticado moderno, como AES-GCM o ChaCha20-Poly1305, de una biblioteca bien revisada. No inventes tu propio esquema.
  • Mantén las claves separadas de los datos y gestiónalas en un gestor de secretos o un servicio de gestión de claves, no en el código ni en la configuración.
  • Aplica hash a las contraseñas con un algoritmo específico como Argon2id, scrypt o bcrypt. No las guardes nunca codificadas ni cifradas de una forma reversible.
  • Usa HTTPS en todas partes para que las credenciales y los tokens viajen cifrados.
  • Codifica después de cifrar, y solo si el canal necesita texto. El orden es primero cifrar y luego pasar a Base64 el texto cifrado.

Riesgos de seguridad al manejar entrada Base64

Aunque Base64 no ofrece ninguna protección, hay consideraciones de seguridad reales cuando tu aplicación acepta Base64 del exterior:

  • Límites de tamaño. Una petición pequeña puede decodificarse en un búfer grande. Limita la longitud del Base64 entrante antes de decodificar para evitar agotar la memoria.
  • Valida el contenido decodificado. Un archivo decodificado puede ser cualquier cosa, sea cual sea el tipo declarado. Comprueba el tipo real de archivo y analiza las subidas como cualquier otro archivo.
  • No confíes en los datos decodificados. Si un valor decodificado se usa en una consulta de base de datos, un comando o HTML, aplica las protecciones habituales: consultas parametrizadas, escape y codificación de salida.
  • Ten cuidado con las URI de datos. No insertes nunca URI de datos proporcionadas por el usuario en enlaces o marcos sin validar, y restríngelas en tu Content Security Policy a los lugares donde las necesites, como img-src.
  • Decodificación estricta. Rechaza la entrada con caracteres fuera del alfabeto en lugar de ignorarlos, para que distintos componentes no interpreten la misma cadena de forma diferente.

Cuándo Base64 está bien

Nada de esto significa que Base64 sea malo. Es exactamente la herramienta adecuada para su trabajo: transportar datos binarios por canales de texto. El error es pedirle un trabajo para el que nunca se diseñó. Si los datos no son secretos, Base64 por sí solo está bien. Si lo son, cífralos y usa Base64 solo para transportar el texto cifrado.
