Base64 est-il sûr ? Encodage ou chiffrement

Novembre 20267 min de lecture

Une chaîne Base64 comme cGFzc3dvcmQxMjM= a l'air brouillée, et cette apparence pousse beaucoup de gens à la traiter comme une protection. Ce n'en est pas une. Base64 est un encodage réversible, sans clé ni secret, que n'importe qui peut décoder en une seconde. Ce guide explique la différence entre encodage et chiffrement, montre où Base64 est pris pour de la sécurité et donne des règles pratiques pour traiter les secrets et les entrées non fiables.

Encoder n'est pas chiffrer

Les deux notions résolvent des problèmes différents :

  • L'encodage change la représentation des données pour qu'elles puissent transiter par un canal donné. La méthode est publique, il n'y a pas de clé et n'importe qui peut l'inverser. Base64, l'encodage URL et l'hex sont des encodages.
  • Le chiffrement transforme les données pour que seul le détenteur de la bonne clé puisse les lire. Même si la méthode est publique, comme AES, les données restent illisibles sans la clé.
  • Le hachage produit une empreinte de taille fixe qui ne peut pas être inversée. Il sert aux contrôles d'intégrité et au stockage des mots de passe (avec une vraie fonction de hachage de mots de passe).

La chaîne ci-dessus se décode en password123 avec n'importe quel décodeur Base64. Rien dans la transformation ne dépend d'un secret.

Où Base64 est pris pour de la sécurité

L'authentification HTTP Basic

L'authentification Basic envoie Authorization: Basic suivi du Base64 de utilisateur:motdepasse. Le Base64 n'est là que pour que les caractères spéciaux survivent dans un en-tête. Quiconque peut voir la requête peut lire les identifiants, c'est pourquoi l'authentification Basic ne doit être utilisée que via HTTPS.

Les JSON Web Tokens

L'en-tête et la charge utile d'un JWT sont encodés en Base64URL, pas chiffrés. Quiconque détient le jeton peut lire toutes ses revendications. La signature prouve seulement que le jeton n'a pas été modifié ; elle ne cache pas le contenu. Ne mettez ni secrets ni données personnelles sensibles dans un JWT signé standard. Pour en savoir plus, voir Comment les jetons JWT utilisent l'encodage Base64URL.

Les Secrets Kubernetes

Les valeurs d'un manifeste Secret Kubernetes sont encodées en Base64. C'est une exigence de format pour stocker du binaire, pas une protection. Par défaut, les Secrets sont stockés non chiffrés dans le magasin de données du cluster ; ce qui les protège, c'est le contrôle d'accès et le chiffrement au repos facultatif. Traitez le fichier de manifeste comme sensible et gardez-le hors du contrôle de version.

Fichiers de configuration et variables d'environnement

Stocker un mot de passe en Base64 dans un fichier de configuration, une variable d'environnement Docker ou une application mobile ne fait qu'ajouter une étape de décodage pour un attaquant. Tout ce qui est livré dans une application cliente peut être extrait et décodé.

Obscurcissement par les attaquants

Les scripts malveillants cachent souvent des commandes dans du Base64 pour que l'inspection rapide ou une simple recherche de chaînes ne les voie pas. L'option -EncodedCommand de PowerShell, qui attend du Base64 de texte UTF-16, en est un exemple bien connu. Pour les défenseurs, cela signifie que du Base64 inattendu dans les journaux et les scripts mérite un examen plus attentif : décodez-le et lisez-le.

Comment protéger correctement les secrets

  • Utilisez le chiffrement avec un algorithme authentifié moderne comme AES-GCM ou ChaCha20-Poly1305, issu d'une bibliothèque bien auditée. N'inventez pas votre propre schéma.
  • Gardez les clés séparées des données et gérez-les dans un gestionnaire de secrets ou un service de gestion de clés, pas dans le code ni la configuration.
  • Hachez les mots de passe avec un algorithme dédié comme Argon2id, scrypt ou bcrypt. Ne les stockez jamais encodés ou chiffrés de façon réversible.
  • Utilisez HTTPS partout pour que les identifiants et les jetons soient chiffrés en transit.
  • Encodez après avoir chiffré, et seulement si le canal a besoin de texte. L'ordre est : chiffrer d'abord, puis passer le texte chiffré en Base64.

Risques de sécurité liés au traitement d'une entrée Base64

Même si Base64 lui-même n'offre aucune protection, de vraies considérations de sécurité se posent quand votre application accepte du Base64 venu de l'extérieur :

  • Limites de taille. Une petite requête peut se décoder en un grand tampon. Limitez la longueur du Base64 entrant avant de décoder pour éviter l'épuisement de la mémoire.
  • Validez le contenu décodé. Un fichier décodé peut être n'importe quoi, quel que soit le type annoncé. Vérifiez le vrai type du fichier et analysez les envois comme tout autre fichier.
  • Ne faites pas confiance aux données décodées. Si une valeur décodée est utilisée dans une requête de base de données, une commande ou du HTML, appliquez les protections habituelles : requêtes paramétrées, échappement et encodage de sortie.
  • Soyez prudent avec les URI de données. N'insérez jamais d'URI de données fournies par l'utilisateur dans des liens ou des cadres sans validation, et limitez-les dans votre Content Security Policy aux endroits où elles sont nécessaires, comme img-src.
  • Décodage strict. Rejetez les entrées contenant des caractères hors de l'alphabet au lieu de les ignorer, afin que différents composants n'interprètent pas la même chaîne de façons différentes.

Quand Base64 convient

Rien de tout cela ne signifie que Base64 est mauvais. C'est exactement le bon outil pour son travail : transporter des données binaires par des canaux texte. L'erreur est de lui demander un travail pour lequel il n'a jamais été conçu. Si les données ne sont pas secrètes, Base64 seul convient. Si elles le sont, chiffrez-les et n'utilisez Base64 que pour transporter le texte chiffré.
