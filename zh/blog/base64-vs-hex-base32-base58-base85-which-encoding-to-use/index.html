Base64、十六进制、Base32、Base85：该选哪种编码？

2026年11月阅读时间约 7 分钟

需要把二进制数据表示为文本时，Base64 是默认选择，但绝不是唯一选择。十六进制、Base32、Base58 和 Base85 解决的是同一个问题，只是在体积、可读性和稳健性上取舍不同。选错编码会导致数据膨胀、大小写相关的错误，或让人无法正确输入的字符串。本文用真实测量数据比较它们，并给出一个简单的选择方法。

核心思想：每个字符承载的比特数

每种把字节转成文本的编码都由一个数字决定：每个输出字符承载多少比特的数据。字符集越大，每个字符承载的比特越多，输出越短。

  • 十六进制（Base16）有 16 个符号，每个字符承载 4 比特。
  • Base32 有 32 个符号，每个字符承载 5 比特。
  • Base64 有 64 个符号，每个字符承载 6 比特。
  • Base85 有 85 个符号，平均每个字符承载略高于 6.4 比特。

更大字符集的代价是包含更多标点和大小写混用，这样更难朗读和输入，也更容易被改变大小写或对符号做特殊处理的系统破坏。

实测的体积开销

为了公平比较，我用 Python 标准库对 1000 个随机字节进行了编码，并统计输出字符数：

  • 十六进制（Base16）：2000 个字符（+100%）
  • Base32：1600 个字符（+60%）
  • Base64：1336 个字符（+33.6%）
  • Base85 / Ascii85：1250 个字符（+25%）

Base58 的字符集不是 2 的幂，所以长度取决于数据，但实际上介于 Base64 和 Base32 之间，开销约为 37%。

十六进制（Base16）

十六进制用 0-9 和 a-f 中的两个字符表示每个字节。它效率最低，但也最易读，因为一个字节总是恰好对应两个字符，可以直接看到每个字节的值。

Hello → 48656c6c6f

适用于：哈希和校验和（SHA-256 摘要几乎总是以十六进制显示）、颜色、MAC 地址、调试转储，以及任何需要人逐字节检查的内容。由于只使用数字和字母，它在实践中也不会遇到大小写和符号问题。

Base32

Base32 使用字母 A-Z 和数字 2-7。它的设计目的是在不区分大小写的系统中保持安全，并避免外形相近的字符，例如 0 和 O、1 和 I。

Hello → JBSWY3DP

适用于：需要人输入或朗读的值，以及存放在不区分大小写的地方（如某些文件系统和 DNS 名称）的值。最知名的例子是用验证器应用设置双因素认证时显示的密钥。输出会用 = 填充到八个字符的倍数。

Base64

Base64 使用 A-Z、a-z、0-9、+ 和 /。它是紧凑性与通用支持之间最好的通用折中：每种语言都内置支持，电子邮件、数据 URI、JSON API 和许多协议也都期望使用这种格式。

Hello → SGVsbG8=

适用于：在 JSON、XML、HTML 和 CSS 中嵌入文件、电子邮件附件、PEM 文件中的加密密钥和证书，以及大多数传输二进制数据的 API。URL 安全变体 Base64URL 把 + 和 / 换成 - 和 _；参见 Base64URL 与 Base64 的区别。

Base58

Base58 是去掉了易混淆字符的 Base64：它省略了 0（零）、O（大写字母 O）、I（大写字母 I）、l（小写字母 L），以及符号 + 和 /。结果是一个便于手工抄写的字符串，而且由于没有标点，在大多数程序里可以双击选中。

适用于：需要人工抄写的标识符，例如加密货币地址和一些短 ID。它的缺点是，与 2 的幂字符集不同，编码和解码需要大数运算，所以速度较慢，不适合大数据。它也不属于大多数标准库，通常需要额外安装软件包。

Base85（Ascii85）

Base85 把四个字节打包成五个字符，是这里各种文本编码中开销最低的：25%。它使用包含许多符号的大字符集，因此很紧凑，但在标点有特殊含义的场合并不方便。

适用于：空间很重要且传输媒介可控的格式，例如 PDF 和 PostScript。Git 使用一种变体来嵌入二进制补丁。Python 提供 base64.a85encode() 和 base64.b85encode()，但在其他语言中的支持不如 Base64 普遍。

快速选择指南

  • 需要人读取字节（哈希、调试）？用十六进制。
  • 需要人输入或口述，或必须经得起大小写转换？用 Base32（若大小写得以保留，也可用 Base58）。
  • 机器通过文本 API、JSON、HTML 或电子邮件交换二进制数据？用 Base64。
  • 值要放进 URL、文件名或 JWT？用 Base64URL。
  • 每个字节都很宝贵，且你控制两端？可以考虑 Base85，更好的做法是完全避免文本编码，直接发送原始字节。

最好的编码有时是不编码

上面每种编码都会增加开销。如果你的协议可以承载原始字节，例如使用 multipart/form-data 的二进制上传、数据库中的二进制列或 gRPC，就直接用它。只有在通道强制要求时，才使用文本编码。
