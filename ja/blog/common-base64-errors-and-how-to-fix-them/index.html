よくあるBase64エラーと解決方法

2026年11月読了時間約8分

Base64は単純ですが、プログラミングで最も分かりにくいエラーメッセージのいくつかを生み出します。Incorrect padding、Invalid character、The input is not a valid Base-64 string などです。メッセージは言語によって異なりますが、原因はほとんど常にごく少数の同じものです。このガイドでは、確認すべき順にそれらを並べ、それぞれの症状、原因、解決策を示します。

最初のステップ：文字列を見る

コードを変更する前に、デコードしようとしている実際の文字列を見てください。4つの簡単な確認で、ほとんどの疑問に答えが出ます。

  • - や _ を含んでいますか？それなら標準のBase64ではなくBase64URLです。
  • + や / を含んでいますか？それなら標準のBase64です。
  • 末尾が = または == になっていますか？なっているべきなのにそうでなければ、パディングが取り除かれています。
  • data: で始まっていますか？それならデータURIで、Base64なのはカンマより後の部分だけです。

1. パディングの欠落または誤り

症状：Incorrect padding（Python）、illegal base64 data at input byte N（Go）、Invalid length for a Base-64 char array（.NET）。

原因：末尾の = が取り除かれたため、文字列の長さが4の倍数になっていません。JWT、URL、一部のAPIでは普通のことです。

解決策：デコードの前に不足しているパディングを追加します。必要な = の数は (4 - 長さ % 4) % 4 です。

def fix_padding(s): return s + '=' * (-len(s) % 4)

便利な妥当性チェックがあります。有効なBase64文字列は、パディングの有無にかかわらず、長さを4で割った余りが1になることは決してありません。長さ % 4 == 1 なら、データが切り詰められているか壊れており、パディングを足しても直りません。

2. 標準とURLセーフの文字セットの取り違え

症状：Invalid character や Illegal base64 character 2d（2d はハイフンの16進コード）、またはエラーなくデコードできるが結果が間違っている。

原因：Base64URL文字列（- と _ を含む）が標準デコーダーに渡された、またはその逆です。

解決策：データに合ったデコーダーを使うか、先に文字を変換します。URLセーフから標準に直すには、- を + に、_ を / に置き換えます。それぞれがいつ使われるかはBase64URLとBase64の違いをご覧ください。

3. プラス記号がスペースになる

症状：デコードしたデータが壊れている、またはデコーダーがスペースについて文句を言う。ただしURLやHTMLフォームを経由した値でのみ起こります。

原因：URLのクエリ文字列やフォームの本文では、+ はスペースを意味します。パーセントエンコードせずにURLに入れた標準Base64の値は、+ がスペースに置き換わって届きます。

解決策：標準のBase64をエスケープせずにURLへ入れてはいけません。パーセントエンコードする（+ は %2B、/ は %2F、= は %3D）か、より良い方法としてBase64URLを使います。受信側での救済策としては、デコード前にスペースを + に置き換えます。

4. 空白文字と改行

症状：Javaでの Illegal base64 character 20（スペース）や 0a（改行）、.NETでの FormatException、または長い値でのみ失敗する。

原因：値が76文字で折り返されている、メールやPEMファイルからコピーされた、または末尾に改行がある。

解決策：デコード前に空白文字を取り除きます（Pythonでは re.sub(r'\s+', '', s)、JavaScriptでは s.replace(/\s+/g, '')）。あるいはJavaのMIMEデコーダーのように、空白を許容するデコーダーを使います。コマンドラインでエンコードするときにecho が追加する末尾の改行にも注意してください。

5. データURIのプレフィックスを含めてしまう

症状：コロンやセミコロンに言及するエラー、または <img src> 属性からコピーしたものをデコードしたときの意味不明な出力。

原因：デコーダーが iVBORw0... だけでなく data:image/png;base64,iVBORw0... を受け取った。

解決策：最初のカンマで分割し、後半だけをデコードします：s.split(',', 1)[1]。画像だけが必要なら、プレフィックスを付けたうえでBase64文字列をそのまま src として使うこともできます。当サイトの画像→Base64変換ツールは両方の形式を出力します。

6. テキストがゴミや奇妙な文字にデコードされる

症状：デコードは成功するが、テキストに Ã©、â€™、疑問符が含まれる。

原因：文字エンコーディングの不一致です。バイトはUTF-8なのに、Latin-1やWindows-1252として解釈されています。逆も起こります。UTF-16でエンコードされたテキスト（.NETの Encoding.Unicode やPowerShellの -EncodedCommand の既定）をUTF-8としてデコードすると、文字の間にヌル文字が現れます。

解決策：両側でテキストのエンコーディングを揃え、特別な理由がなければUTF-8を使います。デコードしたデータがそもそもテキストでない場合（画像、PDF、暗号化されたブロック）、文字列に変換せずバイト列のまま扱います。

7. 二重エンコード

症状：デコードしたら、また別のBase64のような文字列が得られる。多くは ey や SG で始まります。

原因：データが2回エンコードされています。たいていは、コードのある層とライブラリの両方がBase64を適用したためです。

解決策：もう一度デコードし、そのうえで元の場所にある余分なエンコード処理を取り除きます。簡単な見分け方：普通のテキストの本物のBase64は通常アルファベットで始まり、デコード結果それ自体が有効なBase64になるなら、二重エンコードの強い兆候です。

8. 切り詰められた、または壊れたデータ

症状：特定のバイト位置でのエラー、長さを4で割った余りが1、ファイルが部分的にしか開けない。

原因：列数の制限、ログ行の制限、URLの長さ制限、またはコピー＆ペーストのミスで文字列が切られた。

解決策：送信元と宛先で文字列の長さを比較し、途中にあるすべてのシステムの制限を確認します。Base64には誤り検出機能がないので、完全性が必要ならチェックサムを別に送ってください。

9. 入力の種類が違う

症状：ハッシュ、UUID、16進文字列をデコードして、読めないバイトが得られる。

原因：Base64に見える文字列がすべてBase64とは限りません。16進文字列や一部の識別子は、Base64の文字セットにも存在する文字だけを使っているため、デコーダーは喜んで意味のないバイトにデコードしてしまいます。

解決策：データを作った相手に形式を確認します。16進は 0-9 と a-f だけを使い、長さは偶数です。

デバッグ用チェックリスト

  1. 正確な文字列とその長さを出力します。
  2. 文字セット（+/ か -_）を特定します。
  3. 空白文字と data: プレフィックスを取り除きます。
  4. 長さが4の倍数でなければパディングを復元します。
  5. バイト列にデコードし、そのあとでテキストかどうかを判断します。
  6. それでも失敗するなら、decodeb64.comに文字列を貼り付けて、問題がデータにあるのかコードにあるのかを確かめます。
